# 전자결재 공통(Approval Common) Frontend MVP PRD

> 이 PRD는 전자결재 도메인의 **"공통 관심사"** — 기안서 유형(일반/휴가/출장/매출/취소)과 무관하게 공유되는 **상세조회·문서함·결재 워크플로우 액션·공람·첨부** — 만 다룬다. 전자결재 도메인은 규모가 커서 5개 관심사로 절차 분할되며, 이 PRD는 그중 **①공통**이다. 나머지는 별도 PRD가 소유한다: ②일반 기안 작성 / ③출장 기안 작성 / ④연가(휴가) 기안 작성(`docs/prd/6.leave-prd.md`) / ⑤가맹점 매출보고 기안 작성.
>
> **이 PRD가 공통 워크플로우 기능의 원(原) 소유자다.** `docs/ROADMAP(LEAVE).md`의 M2(F606 상세)·M4(기안자 액션 F607~F609)·M5(결재대기함 F619 + 결재자 액션 F610·F611)와 `docs/prd/6.leave-prd.md`의 대응 섹션은 휴가 로드맵이 이 공통 API를 **선점 기술**한 것이다. 본 공통 PRD 확정 이후 LEAVE 로드맵/PRD의 해당 섹션은 재편(overwrite)될 예정이며, 앞으로 상세·문서함·결재/철회/취소·공람·첨부의 사실 원천은 **이 문서**다. 휴가 PRD는 "휴가 유형 슬롯 본문"만 소유한다.
>
> 전역 계약(인증·reissue·에러·`ROLE_003`·페이징 `number+1`·날짜 dayjs·`withCredentials`)은 CLAUDE.md §7 `BACK-END 계약 문서` 관할이며 재서술하지 않는다. 공통 레이아웃 셸(헤더·사이드바·푸터)·인증 배관·`ProtectedRoute`·`apiError`·react-table 페이징 패턴은 기존 자산(`src/shared/**`, `src/features/board/**`·`src/features/attendance/**`)을 **소비**하며 재구축하지 않는다.

## 🎯 핵심 정보

- **목적**: 기안서 유형과 무관하게, 사원이 자신의 문서함(상신함·임시저장함·결재대기함·결재함)에서 기안서를 찾아 상세를 열람하고, 역할(기안자/결재자/공람자)과 결재 상태에 따라 상신·철회·취소기안·승인·반려·공람 지정·첨부 관리를 수행하는 **전자결재 공통 화면**을 구성한다.
- **사용자**: 전 기능 최소 요구 role `EMPLOYEE`(활성 사원). 문서함·상세·워크플로우 액션은 모두 `/api/drafts/**`·`/api/document-boxes/me/**`(둘 다 `EMPLOYEE` 게이트)에 속하며, **세부 권한(기안자 본인 / 결재선 현재 차례 결재자 / 공람 대상자 / 기안서 조회 가능자)은 role이 아니라 문서별 관계로 서버가 최종 판정**한다(일반 403 또는 도메인 에러). 처리 로직은 에러코드에 의존하지 않는다(403→권한 부족, 404→not-found, 재발급 금지).

```
[비인증/세션복원 흐름] — auth-walking-skeleton 관할(재서술 안 함)

[사이드바 "전자결재 > 문서함 홈"] → 문서함 홈(요약) 페이지
  ├ 문서함 요약 카드 4종(결재대기 N · 임시저장 N · 상신 N · 조회가능 N)

[사이드바 "전자결재 > 상신함"] → 상신함 페이지
  ├ 내가 상신한 기안 목록(제목 검색 + 페이징)
  └ 행 클릭 → 기안서 상세 페이지

[사이드바 "전자결재 > 임시저장함"] → 임시저장함 페이지
  ├ 상신 전(UNSUBMITTED) 내 기안 목록(제목 검색 + 페이징)
  └ 행 클릭 → 기안서 상세 페이지(기안자 → 상신/수정 진입)

[사이드바 "전자결재 > 결재대기함"] (뱃지=결재대기 건수) → 결재대기함 페이지

  └ 행 클릭 → 기안서 상세 페이지 → [승인]/[반려]

[사이드바 "전자결재 > 결재함"] → 결재함(조회 가능 문서) 페이지

  └ 행 클릭 → 기안서 상세 페이지(읽기)

[기안서 상세 페이지] (모든 문서함에서 진입 · 공통 셸 + 유형별 본문 슬롯)
  ├ 공통 헤더(제목·기안자·상태 배지·상신일시)
  ├ 유형별 본문 슬롯 ← draftType으로 분기(일반=본문만 / 휴가·출장·매출=각 유형 PRD 소유 섹션)
  ├ 결재선 타임라인(approvers order·승인/반려·사유)
  ├ 공람자 목록(circulations, 읽음 여부) + (기안자) 공람 추가/제거
  ├ 첨부파일 목록(files) + 미리보기/다운로드 + (기안자) 업로드/삭제
  ├ (기안자·UNSUBMITTED) [수정](유형별 작성 PRD)/[상신]
  ├ (기안자·WAITING/IN_PROGRESS) [상신 철회]
  ├ (기안자·APPROVED) [취소 기안 작성]
  ├ (공람 대상자) 최초 조회 시 [공람 읽음 처리]
  └ (내 결재 차례 결재자) [승인]/[반려(사유)]
```

**권한 분기점**

- 라우트 가드(Layer 1): 미인증 → 로그인 리디렉션(auth 관할). 문서함 5종·상세 전부 최소 요구 role `EMPLOYEE`. 별도 role 게이트 없음(전자결재 공통은 전 사원 접근).
- 메뉴 노출: "전자결재" 그룹 전체가 `EMPLOYEE` 공통. role 분기 없음. `ADMIN`은 RoleHierarchy상 당연히 포함.
- 서버 최종 판단(role이 아닌 문서-사원 관계):
  - **상세 조회**(`DRAFT_DETAIL`)는 "기안서 조회 가능자"(기안자·결재선 결재자·공람 대상자)만 → 그 외 접근 시 서버 일반 403 또는 도메인 에러 → 권한 부족/not-found UX(재발급 금지).
  - **상신·철회·취소기안·공람 추가/제거**는 **기안자 본인**만.
  - **승인/반려**는 "미처리 결재자 중 가장 낮은 order = 현재 차례"인 결재자만. 결재선 밖·차례 아님·이미 처리 → 서버 최종 판정.
  - **공람 읽음 처리**는 공람 대상자만, 이미 읽은 건 재처리 불가(서버 판정).
  - **첨부 업로드/삭제**는 기안자 본인만. 프론트는 상세 응답의 역할·상태로 버튼을 노출하되 최종 판단은 서버.

### 2. MVP 필수 지원 기능 — 신규 기능ID 없음(기존 셸/인증 재사용, 참조만)

모든 페이지는 기존 공통 레이아웃 셸의 보호 라우트(`ProtectedRoute`) 하위에 얹힌다. 로그인·세션복원·로그아웃·본인 식별(`GET /api/employees/me`)은 재서술하지 않는다. 4종 문서함 목록은 동일한 행 구조(`DocumentBoxRow`)·페이징·검색을 공유하므로 **단일 공용 목록 컴포넌트(DocumentBoxTable)를 재사용**한다(신규 발명 아님, 재사용 설계). 결재선·공람 지정에 필요한 사원 검색 경로는 **Open Question #1** 참조(발명 금지).

### 3. MVP 이후 기능 / 범위 외 (이번 PRD 명시적 제외)

이 공통 PRD는 **작성/수정을 소유하지 않는다.** 아래는 각 유형별 작성 PRD 또는 다른 도메인 소유:

- **유형별 기안서 생성/수정 API 전부**: `GENERAL_DRAFT_CREATE`/`_CREATE_SUBMISSION`/`_UPDATE`(②일반), `LEAVE_DRAFT_*`(④연가, `docs/prd/6.leave-prd.md`), `BUSINESS_TRIP_DRAFT_*`·`BUSINESS_TRIP_PARTICIPANTS_UPDATE`(③출장), `SALES_DRAFT_*`(⑤매출, `FRANCHISE` 전용) — **각 유형 작성 PRD 관할.** 단, 상세 페이지 셸은 이 유형들의 본문 슬롯이 나중에 꽂힐 **확장 포인트**이며(§설계 요구사항), 상세의 [수정] 버튼은 각 유형 작성 페이지로 라우팅만 한다.
- **유형별 이력 조회**: `MY/DEPT_LEAVE_REQUEST_HISTORY`(④연가), `MY/DEPT_BUSINESS_TRIP_REQUEST_HISTORY`(③출장) — 각 유형 PRD.
- **테마/다크모드·다국어(i18n)·브라우저 푸시 알림** — 전 도메인 공통 제외.

> **설계 요구사항(확장 포인트)**: F701 기안서 상세 페이지는 **공통 셸(헤더·결재선·공람·첨부·액션 버튼) + 유형별 본문 섹션 슬롯**으로 설계한다. 슬롯은 `draftType`으로 분기하며, 실측된 슬롯 계약은 다음과 같다(§참조 계약 매핑에 필드 상세):
> - `draftType == "LEAVE"` → `leave` 객체 렌더(④연가 PRD가 슬롯 본문 컴포넌트 소유)
> - `draftType == "BUSINESS_TRIP"` → `businessTrip` 객체 렌더(③출장 PRD 소유)
> - `draftType == "SALES"` → `sales` 객체 렌더(⑤매출 PRD 소유)
> - `draftType == "GENERAL"` → 유형 슬롯 없음, 공통 `content`만 렌더
> - 취소 기안 → `sourceDraftId`로 원본 기안 링크 표시(취소기안 유형 판별은 Open Question #2)
> 이번 공통 PRD는 **슬롯 계약(어떤 draftType에 어떤 객체가 채워지는지)과 GENERAL 렌더까지** 구현하고, 나머지 유형 슬롯 본문은 미구현 시 "해당 유형 화면 준비 중" 폴백으로 처리한다(Open Question #3).

```
     ├── 임시저장함 — F713 (+진입: 상세 F701 → 상신 F702/수정) (minRole: EMPLOYEE)
     ├── 결재대기함 [뱃지: F711] — F710 (+진입: 상세 F701 → 승인 F705/반려 F706) (minRole: EMPLOYEE)
     └── 결재함 — F714 (minRole: EMPLOYEE)
```

- "전자결재" 그룹은 `src/shared/components/sidebarMenuItems.ts`에 **신규 그룹으로 추가**한다(도메인 밖 발명 아님 — `document-boxes` 계약에 근거). 5개 항목 전부 `minRole: EMPLOYEE`.
- **휴가 로드맵과의 관계**: `docs/prd/6.leave-prd.md`/`ROADMAP(LEAVE).md`는 결재대기함(F619)을 임시로 "휴가 관리" 그룹에 두었다. 본 공통 PRD 확정 이후 결재대기함은 이 "전자결재" 그룹으로 이관되며, 휴가 그룹의 임시 슬롯은 제거된다(휴가 PRD 재편 시 반영). 결재대기함 라우트/화면의 원 소유자는 이 PRD다.
- 기안서 **상세**(F701~F709, F716~F719)와 취소 기안 작성 다이얼로그는 별도 메뉴가 아니라 문서함에서 진입하는 하위 라우트/모달이다.
- 전 항목 `EMPLOYEE` 공통이므로 role 분기 없음. 세부 권한은 서버가 문서별로 판정.

| 상세(첨부 다운로드) | approval/file | `DRAFT_FILE_DOWNLOAD` | Binary/File(attachment) | path `draftId`+`fileId`. `200`. 조회 가능자 |

**공통 enum · 표시 규칙(스니펫/도메인모델 실측):**
- **`ApprovalStatus`:** `UNSUBMITTED`(임시저장/미상신) · `WAITING`(결재대기) · `IN_PROGRESS`(결재진행중) · `APPROVED`(결재완료) · `REJECTED`(결재반려). 목록/상세 응답의 `approvalStatus`는 **표시명 문자열**(예 "결재진행중")로 내려온다.
- **상태 전이(도메인모델):** `(UNSUBMITTED →) WAITING → IN_PROGRESS → APPROVED` / `WAITING·IN_PROGRESS → REJECTED`. 상신은 UNSUBMITTED에서만, 결재자 1명 이상 필수. 승인 가능자 = 미처리 결재자 중 최소 order(현재 차례). 반려 즉시 REJECTED.
- **`Approvers.role`:** `APPROVER`(결재 승인자) · `COOPERATOR`(협조 승인자). 결재선 타임라인 표기에 사용.
- **`draftType`:** String enum(관측값 `BUSINESS_TRIP`; 일반=`GENERAL`, 휴가=`LEAVE`, 매출=`SALES` 추정). **정규 enum 값 집합·취소기안 유형 표기는 미확정 → Open Q#2.**
- **공람 정책(도메인모델):** 공람 대상자는 원본 기안 **결재완료(APPROVED)** 시 조회 가능(`markReadable`). 추가 직후 미열람(`readAt=null`), 이미 읽은 건 재열람 처리 불가.
- **첨부 정책:** `drafts` 도메인 — 허용 확장자 게시판과 동일(`pdf,doc,docx,xls,xlsx,ppt,pptx,txt,csv,png,jpg,jpeg,gif,zip`), 파일당 상한(file-upload.md 표=20MB)과 별개로 **도메인모델 규칙: 기안서당 최대 10개·총 10MB**. 검증 위반 에러 `FILE_001~005`. 상세는 `@docs/backend-contract/file-upload.md` 참조.
- **날짜 포맷:** 상세/목록의 `submittedAt`·슬롯 `startAt`/`endAt`은 `yyyy-MM-dd'T'HH:mm:ss`. 파싱·표기는 전부 dayjs.

## ❓ Open Questions (계약 공백 — 개발 착수 전 확인 필요)

1. **결재선/공람 대상 사원 검색 경로.** 취소 기안 작성(F704)의 `approvers[]`와 공람자 추가(F707)의 `empIds[]`를 지정하려면 사원 검색 UI가 필요하다. `EMPS_FOR_MANAGEMENT`(HR/DEPT_MANAGER 전용)·`NEW_EMP_LIST`(HR 전용)는 일반 사원이 못 쓴다. `DEPT_MEMBERS`(`/api/departments/{deptId}/members`, `EMPLOYEE` 가능)·`DEPTS`로 후보를 조회하는 방식이 유일해 보이는데, **일반 사원의 결재자/공람자 후보 조회 표준 경로**를 확정 필요(휴가 PRD Open Q#1과 동일 이슈 — 공통 컴포넌트로 통합).
2. **`draftType` 정규 enum 값 집합 + 취소기안 유형 표기.** 상세 응답 `draftType`은 String이며 스니펫 관측값은 `BUSINESS_TRIP`뿐이다. `GENERAL`/`LEAVE`/`SALES`는 추정이며, **취소 기안**(도메인모델의 `Leave_Cancel_Draft`/`BusinessTrip_Cancel_draft`)이 별도 `draftType` 값을 갖는지, 아니면 원본 유형 값 + `sourceDraftId!=null`로 판별하는지 확정 필요. 슬롯 분기 로직의 핵심.
3. **미구현 유형 슬롯 폴백 UX.** 이번 공통 PRD는 공통 셸 + GENERAL 렌더만 구현하고, LEAVE/BUSINESS_TRIP/SALES 슬롯 본문은 각 유형 PRD가 소유한다. 해당 유형 PRD 미착수 시 상세의 유형 본문 슬롯과 [수정] 라우팅을 "해당 유형 화면 준비 중" 폴백으로 처리하는 것으로 가정 — 폴백 표기/비활성 범위 확정 필요.
4. **상세 액션 버튼 노출 판정 기준.** "현재 내 결재 차례"(본인이 결재선에 있고 이전 order 전부 처리·본인 미처리), 기안자 상태별 노출(UNSUBMITTED→상신/수정, WAITING/IN_PROGRESS→철회, APPROVED+`cancellationDraftId==null`→취소기안), 공람 읽음 노출(본인이 `circulations[]`에 있고 `readAt==null`)을 상세 응답 필드로 프론트 도출하는 규칙 확정 필요. 최종 판단은 서버(403/도메인 에러 폴백).
5. **`leave`/`sales` 슬롯 하위필드 스니펫 재확인.** `DRAFT_DETAIL` 스니펫 예시가 BUSINESS_TRIP이라 `leave`/`sales` 하위필드는 스니펫에 노출되지 않았다(businessTrip만 실측). `leave{startAt,endAt,leaveType,reservedHours}`·`sales{franchiseId,reportMonth,salesAmount}`는 각각 휴가 PRD 실측/매출 작성 request-fields 기반 추정이므로, 휴가·매출 유형 상세 케이스 스니펫(REST Docs)로 최종 대조 권장.
6. **첨부 업로드 다중/단건 여부.** `DRAFT_FILE_UPLOAD` request-parts는 part명 `file`(단수)로 1회 1파일이나, 도메인 규칙은 기안서당 최대 10개다. 다중 파일 UX(연속 업로드 vs 다중 선택 1요청)와 총 10MB/10개 클라이언트 사전검증 범위 확정 필요(`@docs/backend-contract/file-upload.md`).
7. **문서함 목록의 유형 뱃지/필터.** 4종 문서함 행(`DocumentBoxRow`)에 `draftType`이 없어 목록 단계에서 유형 식별·필터가 불가하다(제목/기안자만). 특히 결재대기함의 유형 혼재 식별을 목록 뱃지로 제공할지, 상세 진입 후 분기로만 처리할지 확정 필요(백엔드 `draftType` 목록 노출 요청 여부 포함).
