# 일정(Schedule) 캘린더 Frontend MVP PRD

> 이 PRD는 신규 **schedule 도메인**을 다룬다 — **모든 타입(MANUAL/MEETING/LEAVE/BUSINESS_TRIP)을 아우르는 통합 일정 캘린더 조회·상세 조회**와, **수기(MANUAL) 타입 일정의 직접 CRUD(등록·수정·취소·참여자 추가/제외)**로 구성된다. 스코프는 `api-endpoint.md` 91~100행 `SCHEDULE / MEETING API`의 **schedule 전용 7개 엔드포인트**(`SCHEDULE_CALENDAR`·`SCHEDULE_DETAIL`·`MANUAL_SCHEDULE_CREATE`·`SCHEDULE_PARTICIPANTS_ADD`·`SCHEDULE_PARTICIPANTS_REMOVE`·`SCHEDULE_CANCEL`·`MANUAL_SCHEDULE_UPDATE`)다.
>
> **범위 밖(명시적 제외) — MEETING/LEAVE/BUSINESS_TRIP 타입 일정의 생성/수정/취소.** 도메인모델(`@../docs/도메인모델.md` §Schedule 521~534행)상 회의 일정은 회의 예약 완료 이벤트로, 출장/휴가 일정은 기안서 결재완료 이벤트로 **백엔드가 자동 생성**한다. 즉 **프론트에서 직접 CRUD 가능한 일정은 MANUAL 타입뿐**이고, MEETING/LEAVE/BUSINESS_TRIP는 이미 완료된 각 도메인(회의/휴가/출장)이 만든 일정을 **본 캘린더에서 "조회"만** 한다. 이 세 타입의 관리는 각 도메인 화면(회의 예약 상세·휴가/출장 기안서) 소관이며 본 PRD 밖이다.
>
> **재구축 금지·소비만** — 아키텍처 배관(axios `withCredentials`·QueryClient·`ProtectedRoute`·`hasRequiredRole`·LayoutShell·`handleApiError`·`useZodForm`/`submitWithErrorMapping`·shadcn 폼·sonner·dayjs)은 완성돼 있다. **meeting 도메인이 확립한 FullCalendar 소비 표준을 동형 재사용**한다: `features/meeting/lib/calendarRange.ts`의 `buildCalendarRangeParams(activeStart, activeEnd)`(→ `start`/`end` `yyyy-MM-dd'T'HH:mm:ss` 조립, **SCHEDULE_CALENDAR와 쿼리 포맷 동일**), 제네릭 래퍼 `features/meeting/components/MeetingCalendar.tsx`(`EventInput[]` + `onRangeChange` + `onEventClick` — 도메인 비의존이라 그대로 소비 가능), `features/meeting/lib/mapMeetingRoomReservationsToEvents.ts`(응답 → FullCalendar 이벤트 매핑 어댑터 패턴), `features/meeting/model/meetingKeys.ts`(queryKey 팩토리 패턴). 참여자 지정은 전자결재 `EmployeePicker`(다중 선택, `features/department` 소비)를 재사용한다. **캘린더는 `@fullcalendar/react` 고정(CLAUDE.md §6).**
>
> **전역 계약**(인증·reissue·401/403 분기·`ROLE_002`/`ROLE_003`·날짜 dayjs·`withCredentials`·ApiError `{code,name,httpStatus,message}`)은 CLAUDE.md §7 `BACK-END 계약 문서` 관할이며 여기서 재서술하지 않는다.
>
> **UI 범위 노트** — 본 PRD 단계는 **최소 기능 뷰만 배치**한다. 시각 스타일 다듬기(레퍼런스 `http://localhost:5174/apps/calendar` 참고)는 이후 `adapt-ui`/`ux-ui-stylist` 단계 몫이다.

## 🎯 핵심 정보

- **목적**: 활성 사원이 자신의 조회 가능 범위 일정(수기/회의/휴가/출장)을 하나의 캘린더로 조망하고, 수기 일정을 직접 등록·수정·취소하며 참여자를 추가/제외한다.
- **사용자**: 최소 요구 role `EMPLOYEE`(전 사원). 조회·수기 일정 등록은 활성 사원 누구나. 수기 일정의 수정/취소/참여자 관리는 **일정 소유자 본인**(서버 최종 판정, 상세 응답 `isEditable`로 UI 게이팅). Layer 2(HR/FRANCHISE/FACILITY/IT)·DEPT_MANAGER "같은 부서" 조건과 무관한 도메인.

## 🚶 사용자 여정

```
[비인증] → 로그인(리디렉션, auth 관할) → 세션 복원(부팅 시 reissue 1회 · 본인정보 GET /api/employees/me)

[사이드바 "일정/회의 > 일정 캘린더"] (minRole EMPLOYEE) → 일정 캘린더(P1)
  ├ 캘린더 이벤트 클릭 → 일정 상세(P2, 다이얼로그)
  │     ├ (타입=MANUAL & isEditable=true = 소유자) → 수정 / 참여자 추가 / 참여자 제외 / 일정 취소
  │     └ (타입=MEETING/LEAVE/BUSINESS_TRIP 또는 isEditable=false) → 조회 전용(액션 버튼 미노출)
  └ [일정 등록] → 수기 일정 등록(P3, 다이얼로그) → 성공 시 캘린더 갱신(P1)
```

**권한 분기점**

- 라우트 가드(Layer 1): 미인증 → 로그인 리디렉션(auth 관할). 일정 라우트는 최소 요구 role `EMPLOYEE`(security.md 31행: `/api/schedules/**` → `EMPLOYEE`). 상위 role(DEPT_MANAGER/ADMIN 등)은 RoleHierarchy상 자동 포함.
- 서버 최종 판단(role 아닌 **일정 소유자 관계**·도메인 규칙):
  - **수기 일정 수정/참여자 추가·제외/취소**(F004~F007)는 **일정 소유자만**(계약 "일정 소유자"). 프론트는 상세 응답 `isEditable`(서버 계산 "현재 로그인 사원의 수정 가능 여부")를 액션 노출 힌트로 쓰고, 소유자 아닌 시도는 서버가 403/도메인 에러로 최종 판정 → `handleApiError` 토스트(재발급 금지). 이 소유자 불일치는 부서 불일치(`ROLE_003`)와 다른 코드이므로 프론트는 `code` 비의존으로 처리한다.
  - **타입 게이팅**: MEETING/LEAVE/BUSINESS_TRIP 타입 일정은 수정/취소/참여자 API 대상이 아니다(도메인모델: 수기 일정만 수정 가능). 이들은 `isEditable=false`로 내려오므로 상세는 **조회 전용**으로 렌더한다.
  - **취소 선행조건**: 일정 취소는 "본인 이외 다른 참가자가 있으면 취소 불가"(도메인모델 534행). 프론트는 상세 응답 `participantCount`(소유자 포함)를 힌트로, 소유자 외 참가자가 있으면 "참가자를 먼저 제외해야 취소할 수 있습니다"를 안내하고, 최종 판정은 서버(위반 시 도메인 에러 토스트).
  - **이미 취소된 일정**: `isCanceled=true`면 재취소해도 상태 불변(도메인모델) → 취소 버튼 미노출.

|---|---|---|---|---|

### 3. MVP 필수 지원 기능 — 신규 기능ID 없음(전역 자산 소비)

- **로그인 + 세션 복원 + 회원가입/승인 대기** — auth·shell PRD 관할(`LOGIN`/`REISSUE_TOKEN`/`RETRIEVE_ME_INFO`/`REGISTER`). 본 도메인은 진입 전제로만 사용하며 재구현하지 않는다.
- **본인 empId 획득** — "일정 소유자 본인" 판정 보조·참여자 자기 지정 방지에 `useMeQuery().data?.empBasicInfo.empId`(기존 패턴)를 소비. 단, 액션 노출의 1차 기준은 서버가 내려주는 상세 응답 `isEditable`이다(로딩 전/부재 시 `undefined` → fail-closed, 액션 미노출).
- **참여자 선택 위젯** — F005 추가·F006 제외의 대상 지정에 전자결재 `EmployeePicker`(다중 선택, 전사 검색)를 재사용한다.
- **캘린더 프리미티브** — meeting 도메인의 `buildCalendarRangeParams`·`MeetingCalendar`(제네릭 래퍼)·이벤트 매핑 어댑터 패턴·queryKey 팩토리를 동형 소비(내용 복제 아님, 패턴/공용 래퍼 재사용).

### 4. MVP 이후 기능 / 범위 외 (이번 PRD 명시적 제외)

- **MEETING/LEAVE/BUSINESS_TRIP 타입 일정의 생성/수정/취소** — 각각 회의/휴가/출장 도메인 소관(백엔드 이벤트 자동 생성). 본 캘린더에서는 조회 전용.
- **일정 상세에서 원천 문서(회의 예약·기안서)로의 딥링크** — `SCHEDULE_DETAIL` 응답에 `sourceId`/원천 링크가 없어 프론트에서 딥링크 불가(§계약 실측 메모).
- **부서/공용 일정 별도 관리 화면·반복 일정 편집기(RRULE)** — 계약에 대응 API 없음.
- **테마/다크모드·다국어(i18n)·브라우저 푸시 알림** — 전 도메인 공통 제외.

**계약 실측 메모(스니펫 직접 대조):**

- **시각 포맷 차이(⚠️ 중요):** `MANUAL_SCHEDULE_CREATE`의 `startAt`/`endAt`는 **full datetime `yyyy-MM-dd'T'HH:mm:ss`**(날짜+시각). 반면 `MANUAL_SCHEDULE_UPDATE`의 `startAt`/`endAt`는 **시각만 `HH:mm:ss`**다(일정은 날짜 단위 row라 수정은 그 날짜 row의 시각만 조정, 날짜 이동 불가). `SCHEDULE_CALENDAR`/`SCHEDULE_DETAIL` 응답도 `scheduleDate`(yyyy-MM-dd) + `startAt`/`endAt`(HH:mm:ss)로 날짜·시각을 분리해 내려준다. 전부 dayjs로 조립/파싱.
- **scope(SINGLE/SERIES):** 참여자 추가/제외·취소·수정 4종 모두 `scope` 쿼리(선택, 기본 `SINGLE`) 지원. `SERIES`=동일 일정 묶음(sourceKey) 전체 적용. 수기 일정이 여러 날에 걸치면 날짜 단위로 여러 row가 생기고 공통 `sourceKey`로 묶인다(CREATE 응답의 `sourceKey`).
- **series 멤버십 미노출:** `SCHEDULE_CALENDAR`/`SCHEDULE_DETAIL` 응답에는 `sourceKey`/series 식별 필드가 **없다**. 즉 프론트는 어떤 일정이 여러 날 묶음인지 응답만으로 알 수 없다 → SERIES 적용 UX는 Open Q#1.
- **응답 코드:** 조회 `200`, 수기 등록 `201 { sourceKey }`, **참여자 추가 `201` Empty**, 참여자 제외/취소/수정 `204` Empty.
- **isEditable:** `SCHEDULE_DETAIL` 전용 필드로 서버가 "현재 로그인 사원의 수정 가능 여부"를 계산해 내려준다. 프론트는 이 값(+ `scheduleType=MANUAL`, `isCanceled=false`)으로 액션 버튼을 게이팅한다(소유자/타입을 프론트가 직접 재계산하지 않음).
- **참여자 제외 제약:** `participantIds`에 일정 소유자를 포함할 수 없다(request-fields 제약). 참여자 제외 UI에서 소유자 행은 선택 불가 처리.

## ❓ Open Questions (착수 전 사용자·검증 확인 필요)

1. **scope(SINGLE/SERIES) 노출 UX.** 캘린더/상세 응답에 series 식별 정보가 없어 프론트는 "이 일정이 여러 날 묶음인지" 알 수 없다. **권고:** 수정/참여자/취소 다이얼로그에 "이 날짜만(SINGLE) / 동일 일정 전체(SERIES)" 라디오를 **항상 노출**(기본 SINGLE). 단일 일정이면 SERIES 선택도 SINGLE과 동일 효과. 더미데이터로 여러 날 수기 일정 생성 후 SERIES 동작 실측 권장.
2. **수기 일정 종일(isAllDay) 등록 여부.** `MANUAL_SCHEDULE_CREATE`/`UPDATE` 요청에 `isAllDay` 필드가 없다(응답엔 존재). **권고:** MVP는 시각 지정만 제공(종일 토글 제외), `isAllDay`는 원천 일정(휴가 등 종일성) 캘린더 표시용으로만 소비. 종일 수기 일정이 필요하면 백엔드 계약 확장 논의.
3. **상세/등록/수정 화면 형태(다이얼로그 vs 라우트 페이지).** 레퍼런스 UI(`/apps/calendar`)가 모달 기반이고 도메인이 경량이라 **다이얼로그 권고**. 딥링크(공유 가능 URL)가 필요하면 라우트 페이지로 승격 — 이는 `adapt-ui`/`react-router-developer` 단계에서 결정.
4. **캘린더 조회 범위.** `SCHEDULE_CALENDAR` 권한이 "EMPLOYEE(조회 가능 범위)"로 서버가 범위를 판정한다(본인 소유·참여 일정 등). 부서/공용 일정 포함 여부·추가 필터 필요성은 서버 반환 범위에 의존 → 착수 시 더미데이터로 실측 확인.
