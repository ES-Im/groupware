# 채팅(Chat) Frontend MVP PRD

> 이 PRD는 채팅 도메인 — **채팅방 목록·대화(메시지 열람/실시간 수신/발신)·방 생성·초대·표시명 수정·나가기·즐겨찾기·읽음 위치** — 만 다룬다. 채팅은 REST(채팅 전용 기능ID 10개)와 **STOMP over WebSocket**(`/ws-chat`)이 혼합된 도메인이며, 실시간 발신/수신의 계약 원천은 `@docs/backend-contract/chat-stomp.md`, REST 필드 원천은 `back/build/generated-snippets/<기능ID>/`, 도메인 규칙 원천은 `@../docs/도메인모델.md`(채팅 섹션)다.
>
> **채팅은 "별도의 서비스인 척" 동작하는 도메인이다.** 메인 groupware 셸(사이드바·헤더 레이아웃) 안의 패널/모달이 아니라, 헤더 말풍선 아이콘 클릭 시 **별도의 브라우저 창(팝업)** 으로 뜨는 독립 앱처럼 동작한다. 창 안에서 채팅 전용 레이아웃이 메인 페이지와 독립적으로 렌더·부팅된다(§🪟 채팅 창 UX 구현 방향).
>
> 전역 계약(인증·부팅 시 `reissue`·에러 `ApiError`·`ROLE_003`·`withCredentials`·날짜 dayjs)은 CLAUDE.md §7 `BACK-END 계약 문서` 관할이며 재서술하지 않는다. 공통 인증 배관(토큰 인메모리·부팅 reissue·`GET /api/employees/me`)과 `BlobAvatar`(인증 필요 preview 이미지 blob 로딩), `apiError` 유틸은 기존 자산(`src/shared/**`)을 **소비**한다.

## 🎯 핵심 정보

- **목적**: 사원이 헤더 말풍선 아이콘으로 **별도 채팅 창**을 열어, 내 채팅방을 검색·즐겨찾기 필터로 탐색하고, 방에 들어가 과거 메시지를 무한스크롤로 열람하며 **STOMP 실시간 송수신**으로 대화하고, 방 생성·멤버 초대·표시명 수정·나가기·즐겨찾기·읽음 위치 갱신을 수행하는 독립 채팅 앱을 구성한다.
- **사용자**: 전 기능 최소 요구 role `EMPLOYEE`(활성 사원). 채팅 REST 기능ID 전체가 `EMPLOYEE` 게이트에 속하며, **방 단위 세부 권한("채팅방 멤버" 여부)은 role이 아니라 방-사원 관계로 서버가 최종 판정**한다(비멤버 → 일반 403 또는 `CHAT_*` 도메인 에러). STOMP도 CONNECT에서 access token, SEND/SUBSCRIBE에서 멤버십을 서버가 재검증한다. 처리 로직은 에러코드에 의존하지 않는다(403→권한 부족, 404/`CHAT_*`→not-found, 재발급 금지).

## 🚶 사용자 여정

```
[메인 groupware · 인증 상태] 헤더 말풍선 아이콘(💬) 클릭
        ↓  window.open('/chat', 'haruon-chat', 'popup')  — 이름 고정 → 재클릭 시 기존 창 focus
[채팅 창 부팅(별도 SPA 인스턴스)]
   ├ 인메모리 access token 없음 → 부팅 reissue(`REISSUE_TOKEN`) 1회(refreshToken 쿠키는 same-origin 공유) → access token 자체 획득
   ├ 본인 식별(`RETRIEVE_ME_INFO`)
   ├ STOMP CONNECT ws://localhost:8080/ws-chat (connectHeaders Authorization: Bearer <at>)
   └ reissue 실패(로그인 안 됨) → 팝업 로그인 UX (Open Q#1)
        ↓
[채팅 창 · 채팅방 목록 패널] (route `/chat`)
   ├ 내 채팅방 목록(검색 keyword / 즐겨찾기 필터 isBookmark / unread 배지 / 오래된 방 흐림)
   ├ 방 클릭 → 대화 화면
   ├ 즐겨찾기 별 토글
   └ [새 채팅] → 채팅방 생성 다이얼로그 → 생성 성공 시 새 방 대화 화면으로 이동
        ↓
[채팅 창 · 채팅방 대화 화면] (route `/chat/rooms/:roomId`)
   ├ 상세(멤버·표시명·lastReadMessageId) 로드 + 메시지 목록(cursor 무한스크롤)
   ├ 해당 방 토픽 SUBSCRIBE(/topic/chat/rooms/{roomId}) → 실시간 수신(낙관 메시지 clientMessageId로 dedup)
   ├ 메시지 입력·전송 SEND(/app/chat/rooms/{roomId}/messages) → 낙관 렌더 → 브로드캐스트로 확정
   ├ 새 메시지 도달/방 진입 → 읽음 위치 갱신(lastReadMessageId)
   └ 방 설정 메뉴: 멤버 초대 / 표시명 수정 / 나가기 / 즐겨찾기 → 나가기 성공 시 목록으로
```

**권한 분기점**

- **라우트 성격(Layer 1)**: `/chat`·`/chat/rooms/:roomId`는 메인 셸 밖의 **최상위 채팅 전용 라우트**(별도 `ChatWindowLayout`)다. 최소 요구 role `EMPLOYEE`. 창은 자체 부팅으로 인증하며(reissue), 미인증 시 팝업 로그인 UX(Open Q#1).
- **메뉴 노출**: 채팅은 사이드바 메뉴가 **아니다.** 헤더 말풍선 아이콘(전 사원 공통, `EMPLOYEE`)이 유일한 진입점. `ADMIN`은 RoleHierarchy상 당연히 포함.
- **서버 최종 판단(role 아닌 방-사원 관계)**:
  - **목록 조회**(`CHAT_ROOM_LIST`)는 본인이 참여 중인 방만 서버가 선별.
  - **방 단위 조회/액션**(상세·메시지·초대·표시명·나가기·즐겨찾기·읽음)은 **채팅방 멤버**만 → 비멤버 접근 시 서버 일반 403 또는 `CHAT_*` 도메인 에러 → 권한 부족/not-found UX(재발급 금지, 에러코드 비의존 처리).
  - **STOMP** SUBSCRIBE/SEND는 서버가 멤버십을 재검증 → 비멤버·종료방 대상 프레임은 서버가 거부(STOMP ERROR) → 재구독 금지 + 안내 UX.

### 2. MVP 필수 지원 기능 — 신규 기능ID 없음(내비게이션/기존 자산 재사용)

- **채팅 창 열기(헤더 말풍선)**: `Header.tsx`의 무동작 슬롯(97~101줄)에 `onClick` 배선 → `window.open('/chat', 'haruon-chat', 'popup')`. 백엔드 호출 없는 **순수 UI 내비게이션**(기능ID 없음). 구현 방향은 §🪟.
- **채팅 창 부팅/인증**: 창은 별도 SPA 인스턴스로 뜨므로 기존 부팅 시퀀스(reissue → `GET /api/employees/me`)를 **재사용**한다(전역 계약, 재서술 안 함).
- **STOMP 연결 수립**: 채팅 창에서 단일 STOMP 클라이언트(`@stomp/stompjs`)를 CONNECT(Authorization 네이티브 헤더). F904/F905의 전제 인프라.
- **프로필 이미지**: 응답의 `profileImageUrl`(예 `/api/employees/1/files/7/preview`)은 **인증 필요 바이너리**이므로 `<img src>` 직접 사용 불가 → 기존 `BlobAvatar`(blob fetch) 패턴 재사용.

### 3. MVP 이후 기능 / 범위 외 (이번 PRD 명시적 제외)

- **채팅 파일/이미지 첨부**: 도메인모델 `ChatMessage`는 `content`(텍스트)만 가지며, `file-upload.md`에 `chat` 도메인이 **없다** → 채팅 첨부는 계약에 존재하지 않음. **발명 금지**(향후 백엔드 계약 추가 시 별도 확장).
- **전역 안읽음 알림/헤더 배지**: 열린 방 외 다른 방의 실시간 unread 푸시는 문서화된 목적지가 없다(허용 목적지는 `/topic/chat/rooms/{roomId}` 뿐, `/user` 개인 큐는 prefix만 언급·구체 목적지 미문서화). MVP는 **열린 방만 구독**, 다른 방 unread는 목록 재조회로 갱신. 전역 배지는 범위 외(Open Q#4).
- **메시지 수정/삭제·읽음 확인(누가 읽었는지)·타이핑 인디케이터·이모지 리액션**: 계약 없음 → 제외.
- **테마/다크모드·다국어(i18n)·브라우저 푸시 알림**: 전 도메인 공통 제외(채팅 창은 메인 앱 테마 토큰만 상속).

## 🪟 채팅 창(새 창) UX 구현 방향

**요구사항**: 채팅은 메인 SPA 안의 패널/모달이 아니라 **별도 브라우저 창**으로 뜨는 독립 앱처럼 동작해야 한다. 아래는 현재 스택(React Router 7 · Vite SPA) 내에서 새 기술(iframe·별도 빌드 등) 도입 없이 구현하는 방향이다.

**채택 방향 (스택 내 구현 가능)**
1. **헤더 슬롯 배선**: `src/shared/components/Header.tsx` 97~101줄 말풍선 버튼에 `onClick={openChatWindow}` 연결. `openChatWindow = () => window.open('/chat', 'haruon-chat', 'popup,width=420,height=760')`. **창 이름 `haruon-chat` 고정** → 재클릭 시 브라우저가 기존 창을 재사용·focus(다중 창 난립 방지, 반환된 `window`에 `?.focus()` 호출).
2. **최상위 채팅 라우트**: `createBrowserRouter`에 `/chat`·`/chat/rooms/:roomId`를 **메인 인증 셸(LayoutShell)과 형제인 최상위 라우트**로 등록하고, 전용 `ChatWindowLayout`(사이드바·헤더 없는 독립 크롬)을 쓴다. `window.open('/chat')`은 새 문서를 로드하므로 브라우저가 이를 **별도 창으로 렌더**하고, 그 창은 채팅 전용 레이아웃만 부팅한다 → "별도 서비스인 척" 요구 충족.
3. **창 자체 부팅/인증**: 새 창은 **별도 SPA 인스턴스**(별도 React 트리·별도 react-query 캐시·별도 STOMP 연결)로 뜬다. 인메모리 access token은 창 간 공유되지 않지만, **refreshToken 쿠키는 same-origin 공유**이므로 채팅 창이 부팅 시 `REISSUE_TOKEN` 1회로 access token을 **자체 획득**한다(기존 전역 부팅 로직 재사용). 이후 `RETRIEVE_ME_INFO` → STOMP CONNECT.

**트레이드오프**
- (+) 진정한 창 독립성(별도 창·별도 생명주기·독립 STOMP), 요구사항에 정확히 부합, 새 기술 없음.
- (−) 창을 열 때마다 SPA 재부팅(포털/모달보다 초기 비용 큼) + reissue 1회 왕복. → `haruon-chat` 이름 재사용으로 중복 오픈은 억제.

## ❓ Open Questions (계약 공백 — 개발 착수 전 확인 필요)

1. **채팅 창 미인증(reissue 실패) UX.** 팝업으로 뜬 채팅 창에서 부팅 reissue가 실패(비로그인)하면 전역 계약상 "로그인 페이지 이동"이나, 팝업 내 로그인은 어색할 수 있다. (a) 팝업 내 로그인 폼 표시 vs (b) 팝업 닫고 부모 창에서 로그인 유도 중 확정 필요.
2. **`memberIds` 후보 사원 검색 표준 경로.** 방 생성(F906)·초대(F907)의 `memberIds`를 고르려면 사원 검색 UI가 필요하다. `EMPS_FOR_MANAGEMENT`(HR/DEPT_MANAGER 전용)는 일반 사원이 못 쓴다. `DEPT_MEMBERS`(`/api/departments/{deptId}/members`, `EMPLOYEE` 가능)·`DEPTS`로 후보를 조회하는 방식이 유일해 보이는데, **일반 사원의 대상 사원 조회 표준 경로**를 확정 필요(전자결재 PRD Open Q#1과 동일 이슈 — 공통 사원선택 컴포넌트로 통합 검토).
3. **`CHAT_ROOM_LIST.roomName` null 가능 여부/폴백.** 도메인모델상 커스텀 표시명 기본값은 null이고 view는 참여자 소속·이름으로 표시한다. 그러나 목록 응답에는 참여자 이름이 없고 `joinedMemberCount`만 있다. 목록의 `roomName`이 서버에서 이미 합성된 표시명인지(=null 안 옴), 아니면 null이 내려와 클라 폴백이 필요한지(그럴 경우 폴백용 member 정보가 목록에 없음) 확정 필요.
4. **전역 안읽음 알림/헤더 배지.** 열린 방 외 다른 방의 실시간 unread를 헤더 아이콘 배지로 보여주려면 개인 큐 목적지(`/user/...`)가 필요하나 chat-stomp.md에는 prefix만 있고 구체 목적지가 미문서화다. MVP는 열린 방만 구독하고 나머지는 목록 재조회로 갱신한다. 전역 배지 지원 여부/방식 확정 필요(백엔드 개인 큐 계약 요청 포함).
5. **STOMP 브로드캐스트 프레임 스키마 및 메시지 정렬 순서.** `/topic/chat/rooms/{roomId}`가 push하는 메시지 payload 형태가 chat-stomp.md에 명시되지 않았다. `clientMessageId` echo가 문서화된 점(낙관 렌더 dedup 목적)으로 보아 `CHAT_MESSAGES`의 message item(`id,senderId,clientMessageId,senderName,content,sentAt,profileImageUrl`)과 동일할 것으로 가정하나, 정확한 필드/이벤트 종류(메시지 외 초대·나가기 시스템 이벤트 push 여부) 확정 필요. 아울러 `CHAT_MESSAGES` 응답 한 페이지 내부의 정렬 순서(newest-first vs oldest-first)도 스니펫에 명시되지 않아, 초기 렌더 정렬과 신규 브로드캐스트 append 위치 결정 전에 확인 필요.
6. **재구독/재연결 정책.** access token 만료(30분) 시 STOMP 세션 처리(끊김 감지 → reissue 후 재CONNECT·재SUBSCRIBE), 방 전환 시 이전 토픽 UNSUBSCRIBE, 창 닫힘 시 DISCONNECT 정리의 구체 정책 확정(구현 세부이나 계약상 재연결 신호 부재).

**🔍 1단계: 기능 명세 → 페이지 연결**
F901·F910 → 채팅방 목록 패널 ✅ / F902·F903·F904·F905·F907·F908·F909·F910·F911 → 채팅방 대화 화면 ✅ / F906 → 채팅방 생성 다이얼로그 ✅. 모든 관련 페이지 실존.

**🔍 2단계: 메뉴 → 페이지**
헤더 말풍선(진입점) → 채팅 창(`/chat`) ✅ / 목록 패널(F901·F910, [새 채팅]→F906) → 페이지 존재 ✅ / 대화 화면(F902~F911) → 페이지 존재 ✅. 채팅은 사이드바 미추가(헤더 진입) 명시 ✅.

**🔍 3단계: 페이지 → 역참조**
3개 페이지의 모든 F ID가 기능 명세에 정의됨 ✅. 전 페이지 진입 경로·접근 권한 항목 존재 ✅. 생성 다이얼로그→대화 화면, 목록→대화 화면 도달 경로 명시 ✅.

**🔍 4단계: 계약 근거**
F901·F902·F903·F906·F907·F908·F909·F910·F911(REST 9개) → `api-endpoint.md` "BOARD/MESSAGE/CHAT API"의 10개 CHAT 기능ID(F910이 bookmark/unbookmark 2개 묶음)에서 실존 확인, 필드는 `generated-snippets`(CHAT_ROOM_LIST/DETAIL/MESSAGES/CREATE/INVITE/NAME_UPDATE/READ_POSITION_UPDATE) 실측 ✅. F904·F905(STOMP)는 `chat-stomp.md`(허용 목적지·`ChatClientSend`) 근거로 표기하고 REST 아님을 명시 ✅. 근거 없는 발명 기능 없음(첨부·수정/삭제·전역 알림은 "범위 외"로 격리) ✅.

**🔍 5단계: 누락/고아**
고아 기능·페이지·메뉴 없음 ✅. 채팅 첨부/메시지 수정·삭제/전역 unread 배지는 계약 부재로 "범위 외" 명시(누락 아님) ✅. 새 창 오픈은 순수 UI 내비게이션(기능ID 없음)으로 지원 기능에 분리 ✅. 잔여 계약 공백(팝업 인증 UX·사원 검색·roomName 폴백·전역 알림·브로드캐스트 스키마·재연결)은 Open Questions(#1~#6)로 격리 ✅.

**결과: 5단계 전부 통과. 채팅 도메인 F901~F911(REST 9 + STOMP 2) 개발 착수 가능. Open Questions는 대부분 비블로킹(브로드캐스트 스키마 #5·사원 검색 #2는 착수 전 확인 권장).**
