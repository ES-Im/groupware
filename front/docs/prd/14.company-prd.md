# 회사 정보(COMPANY) 관리 Frontend MVP PRD

> 이 PRD는 `api-endpoint.md`의 **"COMPANY API"** 섹션 5개 기능ID(`COMPANY_INFO`/`COMPANY_REGISTER`/`COMPANY_UPDATE_INFO`/`COMPANY_UPDATE_CONTACT`/`COMPANY_UPDATE_HOME_PAGE_URL`)만 다룬다. 해당 섹션은 원래 인덱스에 누락되어 있었고 2026-07-10 COMPANY 도메인 착수 시 백엔드 컨트롤러·REST Docs 스니펫과 대조해 보강되었다(다른 섹션과 동일하게 신뢰).
> 공통 레이아웃 셸(헤더·사이드바·푸터)과 인증 배관은 `finish_1.auth-walking-skeleton-prd.md` / `finish_2.shell-and-employee-view-prd.md`를 참조하며 재서술하지 않는다. 전역 계약(인증·에러·페이징·날짜·CORS)은 CLAUDE.md §7 `BACK-END 계약 문서` 관할이다.

---

## 🎯 핵심 정보

- **목적**: HARUON 단일 회사의 공개 기본 정보(회사명·위치·대표 이메일·대표 외부 연락처·대표자명·홈페이지 URL)를 열람하고, `ADMIN`이 **최초 등록** 및 기본정보/연락처/홈페이지 URL을 각각 수정(스냅샷 이력 생성)하는 회사 정보 관리 화면을 구성한다.
- **사용자**: 열람은 `EMPLOYEE` 최소 등급 전체 공통(조회 API는 `permitAll`, 읽기 전용). 등록·수정 액션은 `ADMIN` 전용.

**권한 분기점**

- 라우트 가드(Layer 1): 미인증 → 로그인 리디렉션(auth PRD 관할). 회사 정보 페이지 **열람**은 최소 요구 role `EMPLOYEE`(조회 API가 `permitAll`이므로 로그인 셸 안의 EMPLOYEE 가드로 충분하다).
- 관리 액션 노출(Layer 1): `hasRequiredRole(userRoles, 'ADMIN')` 참일 때만 등록 폼·섹션별 편집 진입점을 렌더(`EMPLOYEE`/`DEPT_MANAGER`는 읽기 전용, 편집 UI 자체가 보이지 않음).
- 서버 최종 판단: 등록·수정 엔드포인트는 전부 `ADMIN` 단일 role 판정이며(같은 부서 조건 없음), UI 우회 호출 시 403은 일반 권한 부족 UX로 처리한다. 이 도메인엔 `ROLE_003`(부서 불일치) 유발 기능이 없다.

- 테마/다크모드, 다국어(i18n), 프로필 커스터마이징.

```

```

**메뉴 구조 결정 근거 (판단이 갈리는 지점 — 명시)**

- 현재 `sidebarMenuItems.ts`에는 ADMIN 전용 "설정류" 그룹이 없다(가장 가까운 선례는 업무 권한 기반 "인사관리"(HR)·"가맹점"(FRANCHISE) 그룹). 회사 정보 관리는 업무(Layer 2) 도메인이 아니라 전사 설정 성격이므로 **신규 "설정" 그룹(`minRole: 'ADMIN'`)을 신설**하고 그 하위에 리프 "회사 정보"를 둔다. 자식이 현재 1개뿐이나, 향후 카테고리 관리 등 ADMIN 설정성 화면의 확장 슬롯이 된다.
- **조회 API는 `permitAll`(전 사원 이상 열람 가능)이지만, 화면 진입점은 ADMIN 설정 메뉴로 한정**한다. 회사 정보 도메인의 프론트 개발 주 목적이 ADMIN의 등록·수정 관리이고(로컬 DB 미등록 상태 → ADMIN 최초 등록이 실사용 진입점), 정보성 상시 노출은 별도 위젯/링크가 필요해 후속 범위로 분리했기 때문이다. 부서 관리 PRD의 "조직도"(EMPLOYEE 공통 리프)와 달리 회사 정보를 ADMIN 그룹에 두는 이유가 이것이다.
- 단, 라우트 가드는 `EMPLOYEE`로 둔다(조회 `permitAll` 계약과 정합 — 비-ADMIN이 URL로 직접 진입해도 읽기 전용 뷰가 정상 표시되어야 하며, 편집 UI만 숨는다). 메뉴 노출(ADMIN)과 라우트 가드(EMPLOYEE)의 이 비대칭은 의도된 설계다.
- 등록·수정 액션은 별도 사이드바 항목이 아니라 회사 정보 페이지 안에서 `hasRequiredRole(roles, 'ADMIN')` 조건부 렌더로 노출한다(S2 표준과 동일 헬퍼, 페이지 내부 버튼 단위 게이팅).
- ADMIN은 RoleHierarchy상 전 메뉴 자동 접근(별도 표기 불필요).

| 항목 | 내용 |

| **진입 경로** | 사이드바 "설정 › 회사 정보"(ADMIN 노출). 비-ADMIN은 직접 URL 진입 시 읽기 전용 뷰 |
| **접근 권한** | 최소 요구 role: `EMPLOYEE`(열람, `COMPANY_INFO` — API는 `permitAll`) / 관리: `ADMIN`(등록·수정 전 액션) / 서버 최종 판단: 없음(부서 불일치 조건 없는 순수 ADMIN role 판정) |
| **사용자 행동** | 현재 회사 정보 확인, (미등록·ADMIN) 최초 등록 폼 입력·제출, (등록됨·ADMIN) 섹션별 "편집" → 다이얼로그 입력·제출 |
| **주요 기능** | • 회사 정보 조회(F1401) — 미등록(404) 시 ADMIN에겐 "최초 등록" CTA, 비-ADMIN에겐 "등록된 회사 정보가 없습니다" 빈 상태 • (ADMIN·미등록) **최초 등록** 폼(F1402, RHF+zod: 7필드 전부 required — 아래 §계약 매핑 제약 준수, `editedAt`은 제출 시각 자동 주입) • (ADMIN·등록됨) **기본정보 수정** 다이얼로그(F1403) • (ADMIN·등록됨) **대표 연락처 수정** 다이얼로그(F1404) • (ADMIN·등록됨) **홈페이지 URL 수정** 다이얼로그(F1405) — F1403/F1404는 최소 1개 필드 변경 시에만 제출 허용(도메인 규칙: 변경 요청에 하나 이상의 변경 값 필수) |
| **다음 이동** | 등록/수정 성공(204) → 다이얼로그·폼 닫힘 + `COMPANY_INFO` 쿼리 invalidate(현재 스냅샷 재조회) + 성공 토스트 / 입력 검증 실패 → 폼 필드 에러(zod) / 등록 시 이미 존재(400, `COMPANY_002`) → "이미 등록된 회사 정보가 있습니다" 안내(`error.code === 'COMPANY_002'` 분기) + 조회 재조회로 상태 동기화 / 수정 시 `editedAt`이 현재 스냅샷보다 이전인 경우 등 서버 미처리 예외(500) → 일반 에러 토스트(sonner) / 403(비-ADMIN 우회 호출) → 권한 부족 UX / 그 외 실패 → 에러 토스트(sonner) |

**폼 UX 결정 (수정 API 3분할 대응)**

- 백엔드 수정 API가 기본정보/연락처/홈페이지 3개로 분리되어 있으므로, **등록 후 화면은 3개 섹션 + 섹션별 편집 다이얼로그**로 구성하고 각 다이얼로그 제출이 대응 API 1개만 호출한다(부서 상세 PRD의 "관리 액션별 다이얼로그" 패턴 복제). 임의의 4번째 통합 수정 API를 발명하지 않는다.
- **최초 등록만 단일 폼**으로 7개 필드를 한 번에 받아 `COMPANY_REGISTER` 1회 호출한다.
- `editedAt`은 사용자 입력 필드가 아니라 **제출 시점의 클라이언트 현재 시각**을 `YYYY-MM-DDTHH:mm:ss`(초 단위, 타임존/밀리초 없음)로 자동 주입한다. 도메인 규칙상 새 스냅샷의 `editedAt`은 현재 스냅샷보다 이후여야 하므로, 서버가 이를 거부하면(동일 초 재제출/시계 오차 등) 에러 토스트로 처리한다.

> **참고**: 로그인/회원가입/승인 대기, 공통 셸(헤더·사이드바·푸터)은 `finish_1.auth-walking-skeleton-prd.md`/`finish_2.shell-and-employee-view-prd.md` 관할이며 이 PRD에서 재정의하지 않는다.

## 📝 판단·전제 요약 (team-lead 확인 요망 지점)

PRD 생성 중 계약만으로 자동 확정되지 않아 합리적 기본안을 택한 지점이다. 개발 착수 전 이견 있으면 조정한다.

1. **메뉴 배치**: 조회가 `permitAll`(전 사원 열람 가능)임에도 화면 진입점을 ADMIN 신규 "설정" 그룹으로 한정했다(비-ADMIN 상시 노출 위젯은 후속). team-lead의 "ADMIN 전용 설정 그룹 신설" 지시와 조회 접근성을 절충한 결과 — 라우트 가드는 EMPLOYEE로 열어 둠.
2. **`editedAt` 자동 주입**: 사용자 입력이 아니라 제출 시점 클라이언트 현재 시각을 전송한다(도메인 규칙: 새 스냅샷은 현재 스냅샷보다 이후). 수동 입력 UI를 원하면 변경 필요.
3. **수정 폼 3분할**: 3개 API에 맞춰 섹션별 편집 다이얼로그로 분리(단일 폼 통합 전송 대신). 부서 상세 PRD 패턴 복제.
