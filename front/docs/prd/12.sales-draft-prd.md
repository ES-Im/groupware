# 매출 기안(Sales Draft) 작성/수정·본문 렌더 Frontend MVP PRD

> 이 PRD는 전자결재 도메인 5분할 중 **⑤매출 기안 관심사** — 매출 기안서(`sales` 슬롯 non-null)의 **작성(임시저장 생성 / 생성+상신)·수정**과 **상세 페이지의 매출 슬롯 본문 렌더**, 그리고 그 작성/수정 폼이 소비하는 **가맹점 선택 UI(`FranchisePicker`) + 신규 `features/franchise` 얇은 조회 슬라이스** — 만 다룬다. 유형과 무관한 **상세조회·문서함 4종·상신/철회/취소·승인/반려/공람·첨부 뷰·결재대기함**은 **①공통(`docs/prd/7.approval-common-prd.md`, 구현 완료 `src/features/approval/**`)** 소유이며 여기서 재구현하지 않고 **소비**한다. 작성/수정 폼·유형 판별 술어·상세 본문 컴포넌트·`[수정]` 분기 배선은 **②일반(`docs/prd/8.general-draft-prd.md`)·③출장(`docs/prd/10.businesstrip-draft-prd.md`)·④연가(`docs/prd/11.leave-draft-prd.md`, 셋 다 구현 완료)** 가 확립한 선례를 **동형 복제**한다.
>
> **경계 요약** — ⑤가 소유: 매출 기안 작성 페이지·수정 페이지, 그 API/mutation/query(2개 DRAFT 기능ID + 1개 FRANCHISE 조회 기능ID), 매출 폼 zod 스키마, 매출 상세 본문 컴포넌트(`SalesDraftBody`, ①의 `DraftTypeBody` "준비 중" 폴백 교체), 유형 판별 술어 `isSalesDraft`(슬롯-null), `SalesSlot` 구체 타입 확정, **신규 `features/franchise` 얇은 슬라이스**(가맹점 목록 조회 `getFranchises`+훅 **하나만**)와 `features/approval`의 가맹점 선택 UI `FranchisePicker`, 사이드바 "전자결재" 그룹 "매출 기안 작성" 신규 1항목, 상세 `[수정]` 버튼의 매출 분기 라우팅 **요구사항**(실제 배선은 라우팅 통합 마일스톤). ⑤가 소비(①/②③④소유, 재구현 금지): `DraftDetailResponse.sales: SalesSlot`(①타입, import/확정)·상세 페이지·`DrafterActions`(상신/철회/취소 + `[수정]` 노출 판정 `resolveDrafterActions.canEdit`)·`ApproverActions`(승인/반려)·**문서함 4종·결재대기함**(상신함/임시저장함/결재대기함/결재함 — 이력 조회 전량 커버)·`EmployeePicker`(결재선 선택)·`ApproverParam`·`approvalKeys`·`useDraftDetailQuery`(수정 프리필)·첨부 업로드(F716)·**본인 empId(`useMeQuery().data?.empBasicInfo.empId`, ①이 이미 확립·②③④ 전역 재사용 패턴)**. 배관: axios·QueryClient·`handleApiError`·`ProtectedRoute`·LayoutShell·`useZodForm`/`submitWithErrorMapping`·shadcn 폼·sonner·dayjs.
>
> **얽힘 확인(결정 사항)** — `api-endpoint.md` 전수 검색 결과 매출 **기안**(`SalesDraft`) 관련 기능ID는 `SALES_DRAFT_CREATE`·`SALES_DRAFT_CREATE_SUBMISSION`·`SALES_DRAFT_UPDATE` **3개가 전부다. 매출 기안 전용 이력조회 API는 존재하지 않는다**(LEAVE/BUSINESS_TRIP과 달리 `MY_SALES_*`/`DEPT_SALES_*` 부재, 전수 확인됨) — 이력은 ①공통 문서함 4종으로 전부 커버되므로 **별도 이력 페이지를 만들지 않는다**. 가맹점 선택 UI를 위한 `FRANCHISE_LIST`(목록 조회) **하나만** 신규로 만든다. `FRANCHISE_*`(가맹점 CRUD/교육/문의/메모)와 `FRANCHISE_SALES_YEARLY/MONTHLY/DAILY`(외부 동기화 배치 aggregate `Franchise_daily_sales` — 매출 **기안**과 무관)는 전부 **범위 밖**(향후 "가맹점" 도메인 build-domain 사이클).
>
> 전역 계약(인증·reissue·에러·`ROLE_003`·페이징 `number+1`·날짜 dayjs·`withCredentials`)은 CLAUDE.md §7 `BACK-END 계약 문서` 관할이며 재서술하지 않는다.

## 🎯 핵심 정보

- **목적**: 가맹점 담당 권한(`FRANCHISE`)을 가진 사원이 **매출 기안서(제목·본문·대상 가맹점·매출 보고월·매출액·결재선·첨부)** 를 작성해 임시저장하거나 바로 상신하고, 상신 전(UNSUBMITTED) 기안을 수정하며, 상세 페이지에서 매출 슬롯 본문을 열람한다. 작성 후에는 ①공통의 상세·문서함·워크플로우로 이어지고, 이력 조회도 ①의 문서함 4종을 그대로 사용한다.
- **사용자**: 작성·수정 모두 최소 요구 role `FRANCHISE`(수정은 **기안자 본인 + UNSUBMITTED**만 — 서버 최종 판정). `ADMIN`은 RoleHierarchy상 `FRANCHISE`를 자동 포함(메뉴·라우트 자동 접근). 매출 기안 승인/반려는 결재선에 지정된 결재자(role·부서 무관, 서버 판정)가 **결재대기함**(①)을 통해 상세로 진입해 처리한다.

## 🚶 사용자 여정

```
[사이드바 "전자결재 > 매출 기안 작성"] (minRole FRANCHISE 노출) → 매출 기안 작성 페이지
  ├ 제목·본문 + 대상 가맹점(FranchisePicker=⑤) + 매출 보고월(reportMonth)·매출액(salesAmount) 입력
  │   + 결재선 지정(EmployeePicker=①) + (선택) 첨부
  ├ [임시저장으로 생성](SALES_DRAFT_CREATE, 201 {draftId})
  │    └ 성공 → 생성된 기안 상세 페이지(①) → (기안자·UNSUBMITTED) 상신/수정/첨부
  └ [생성 후 상신](SALES_DRAFT_CREATE_SUBMISSION, 201 {draftId}, 결재선 최소 1명 사전검증)
       └ 성공 → 생성된 기안 상세 페이지(①, WAITING)

[전자결재 > 임시저장함(①) 또는 상신함(①)] → 행 클릭 → 기안서 상세 페이지(①)
  ├ 본문 = 매출 상세 본문(SalesDraftBody=⑤가 DraftTypeBody 폴백 교체): 가맹점명·보고월·매출액 렌더(read-only)
  ├ (기안자·UNSUBMITTED) [수정] 버튼(DrafterActions=①) → isSalesDraft 분기(⑤ 요구사항, 라우팅 통합 배선) → 매출 기안 수정 페이지
  │     ├ 기존 값 프리필(DRAFT_DETAIL 소비=①: sales 슬롯 + 결재선)
  │     └ [저장](SALES_DRAFT_UPDATE, 204) → 성공 → 상세 페이지로 복귀
  ├ (기안자·WAITING/IN_PROGRESS) [상신 철회]·(APPROVED) [취소 기안 작성] — ①소유
  └ (결재선 결재자·현재 차례) [승인]/[반려] — ①소유(ApproverActions), 결재대기함(①) 경유 진입

[전자결재 > 결재대기함(①)] → 매출 기안 상세 진입 → 승인/반려 (매출 이력·결재 조회 전량 ①문서함 4종이 커버)
```

**권한 분기점**

- 라우트 가드(Layer 1+2): 미인증 → 로그인 리디렉션(auth 관할). 작성·수정 라우트는 최소 요구 role `FRANCHISE`(security.md: `/api/drafts/sales/**` → `FRANCHISE`, RoleHierarchy상 `ADMIN` 자동 포함). `hasRequiredRole('FRANCHISE')`로 사이드바·라우트 게이팅, 서버가 최종 판단.
- 서버 최종 판단(role 아닌 문서-사원 관계·도메인 규칙):
  - **작성**(`SALES_DRAFT_CREATE`/`_CREATE_SUBMISSION`)은 서버가 `emp.getSystemRoles().contains(FRANCHISE)`를 **강제 검증**한다. 프론트는 노출만 담당(재발급 금지, 위반 시 권한 부족 UX).
  - **`franchiseId`는 서버가 담당 여부를 검증하지 않는다**(`SalesDraftService.findFranchise`는 `findById`로 **존재 여부만** 확인). 즉 서버는 임의 `franchiseId`를 허용한다 → 프론트는 "내 담당 가맹점"을 **우선 노출**하되 전체 가맹점 검색도 허용(과도한 제약 없음, §FranchisePicker 정책).
  - **`salesAmount`는 0보다 커야 한다**(백엔드 `SalesDraft.validateSalesInitParam` state 검증, "매출액은 마이너스가 될 수 없음" — 0 이하 전부 거부). 백엔드 타입 `long` → **양의 정수**(zod `.positive().int()`). 프론트 사전검증 + 서버 최종 판정.
  - **수정**(`SALES_DRAFT_UPDATE`)은 **기안자 본인 + 대상 UNSUBMITTED**만(②③④ 동형). 그 외 접근 시 서버 403/도메인 에러 → 권한 부족/처리 불가 UX(재발급 금지, 에러코드 비의존).
  - **상신 시 결재선** 최소 1명 필요(도메인 규칙) → 서버 최종 판정. 프론트는 `[생성 후 상신]`에서 결재선 사전검증(②Open Q#1 정책 복제).

### 1. MVP 핵심 기능

|---|---|---|---|---|
| **[F760]** | 매출 기안서 작성(임시저장 생성 / 생성+상신) | 제목·본문 + 대상 가맹점(`franchiseId`)·매출 보고월(`reportMonth`)·매출액(`salesAmount`) + (선택) 결재선(`param.approvers`) + (선택) 첨부로 매출 기안 생성. 한 폼의 **분리 버튼 2개**: `[임시저장으로 생성]`(UNSUBMITTED, `SALES_DRAFT_CREATE`) / `[생성 후 상신]`(WAITING, `SALES_DRAFT_CREATE_SUBMISSION`, 결재선 ≥1 사전검증). 둘 다 `201 {draftId}` → 생성 기안 상세로 이동. body는 **`param{title,content,approvers?}` + 최상위 형제 `franchiseId/reportMonth/salesAmount`의 혼합 구조**(③출장·④연가와 동형, ②일반의 평탄 구조와 다름 — 임의 평탄화 금지). `franchiseId`/`reportMonth`/`salesAmount` 모두 **필수**, `salesAmount`는 양의 정수 | `SALES_DRAFT_CREATE` / `SALES_DRAFT_CREATE_SUBMISSION` | 매출 기안 작성 페이지 |

### 2. MVP 필수 지원 기능 — 신규 기능ID 없음(①/②③④공통 자산 소비·배선·타입 보강만)

⑤는 다음을 **재구현하지 않고 소비하거나, ①소유 지점에 배선/타입 확정만** 추가한다(경계 = 헤더 인용 블록):

- **매출 상세 본문 렌더(`SalesDraftBody`)** — ①의 `DraftTypeBody`가 현재 `draft.sales != null`이면 "준비 중" 폴백(`TypeSlotFallback typeName="매출"`)을 렌더한다(`components/detail/DraftTypeBody.tsx`). ⑤는 이 분기를 **실제 매출 본문 컴포넌트로 교체**한다(④`LeaveDraftBody`처럼 **read-only, 참여자/공람 뮤테이션 없음**): `sales` 슬롯(`franchiseName`·`reportMonth`·`salesAmount`)과 공통 `content`를 렌더. 데이터는 `DRAFT_DETAIL`(F701, ①)이 이미 내려준 `sales` 슬롯 소비 — 신규 조회 없음. `salesAmount`는 천 단위 구분 표기(예: `1,000,000원`), `reportMonth`는 `yyyy-MM` 그대로 또는 dayjs로 "2026년 4월" 포맷.
- **`SalesSlot` 구체 타입 확정** — 현재 `model/draftDetail.ts:80`의 `SalesSlot = Record<string, unknown>`(①이 슬롯 미확정으로 남겨둠)을 `{ franchiseId, franchiseName, reportMonth, salesAmount }` 구체 타입으로 좁힌다. 백엔드 DTO(`DraftDetailResponse.SalesDraftDetail(Long franchiseId, String franchiseName, YearMonth reportMonth, Long salesAmount)`) 소스 대조로 확정 — `reportMonth`(`YearMonth`)는 JSON 직렬화 시 `"yyyy-MM"` 문자열, `franchiseName`은 상세조회에만 존재(요청 body엔 없음, 표시용).
- **상세 `[수정]` 매출 분기 배선(F761 진입) — 요구사항만 기술, 실제 배선은 라우팅 통합 마일스톤 전담** — ①의 `DrafterActions.handleEdit`는 현재 `isGeneralDraft`·`isBusinessTripDraft`·`isLeaveDraft`를 분기하고 매출은 "준비 중" 토스트 폴백이다. 라우팅 통합 마일스톤이 **`isSalesDraft(draft)` 분기를 추가**해 매출 기안 수정 페이지로 `navigate`한다. 노출 판정(`canEdit` = 기안자 + UNSUBMITTED)은 ①이 이미 계산(재작성 금지).
- **유형 판별 술어 `isSalesDraft`** — `④isLeaveDraft`(`draft.leave != null`)와 동형으로 `draft.sales != null`(`lib/isSalesDraft.ts`). `draftType` 문자열 비교 금지(백엔드 `getClass().getSimpleName()`, 스니펫 값 outdated). 상세 `[수정]` 라우팅과 수정 페이지 진입 가드가 공유.
- **본인 empId 획득** — FranchisePicker "내 담당 가맹점" 우선 노출(`managerId`=본인 empId)은 `useMeQuery().data?.empBasicInfo.empId`(`features/employee/model/me.ts`의 `EmpBasicInfo.empId: number`)를 그대로 쓴다. 이 필드는 ①이 이미 확립해 `ApproverActions`·`AttachmentSection`·`resolveDrafterActions`·`BusinessTripDraftBody` 등 전자결재 전역이 재사용 중인 표준 패턴이며, 로딩 전/부재 시 `undefined`이므로 fail-closed(담당 가맹점 필터 미적용 → 검색 fallback)로 처리한다. `authStore.ts`의 `AuthUser`(zustand 로그인 스냅샷)는 별개 자산이며 건드리지 않는다.
- **`EmployeePicker`(제어형)·`ApproverParam{approverId,role,order}`** — 결재선 선택 UI·payload 타입(①소유). 선택 순서 → `order`(1-base), `role`='APPROVER' 고정(②③④선례 동일).
- **문서함 4종·결재대기함**(상신함/임시저장함/결재대기함/결재함, ①소유) — 매출 기안 이력·결재 조회를 **전량 커버**한다(매출 전용 이력 API 부재이므로 이것이 유일·표준 경로). ⑤는 별도 조치 없음(재추가 금지).
- **`useDraftDetailQuery`(F701)·첨부 업로드 F716 `DRAFT_FILE_UPLOAD`(`useDraftFileUploadMutation`)** — 수정 프리필·본문 렌더 소스, 첨부는 생성 응답 `draftId`로 재사용(②③④와 동일, 상세 첨부 영역=①에서 관리 권고). 파일 정책 `@docs/backend-contract/file-upload.md` + `@../docs/도메인모델.md`.
- **폼 배관** `useZodForm`/`submitWithErrorMapping`(`@/shared/lib/form`)·`handleApiError`·`approvalKeys`(성공 후 `all` invalidate) — ②③④선례 동일.

### 3. MVP 이후 기능 / 범위 외 (이번 PRD 명시적 제외)

- **타 유형 슬롯 작성/수정 전부**: `GENERAL_DRAFT_*`(②), `BUSINESS_TRIP_DRAFT_*`(③), `LEAVE_DRAFT_*`(④) — 각 유형 PRD 관할. ⑤는 매출만.
- **상세조회·문서함 4종·상신/철회/취소·승인/반려·공람·첨부 뷰·워크플로우 액션·결재대기함** — ①공통 소유. "재사용"으로만 언급, 신규 F 부여 없음.
- **매출 기안 전용 이력 페이지** — **만들지 않는다**(전용 이력 API 부재, ①문서함 4종이 상신/임시저장/결재대기/결재 이력 전량 커버).
- **가맹점 도메인 본체 전부**: `FRANCHISE_DETAIL/CREATE/UPDATE/STATUS_UPDATE/MANAGER_UPDATE/MEMO_*`(가맹점 CRUD), `FRANCHISE_EDUCATION_*`, `FRANCHISE_INQUIRY_*` — "가맹점" 도메인 build-domain 사이클 몫. ⑤는 `FRANCHISE_LIST`(선택 UI용 목록 조회) **하나만** 소유.
- **`FRANCHISE_SALES_YEARLY/MONTHLY/DAILY`**(`/api/franchises/{franchiseId}/sales/...`) — **완전히 다른 aggregate**(`Franchise_daily_sales`, 외부 API/MOCKOON 동기화 배치)이며 매출 **기안**(`SalesDraft`)과 무관. 절대 혼동 금지. 사이드바 "가맹점" 그룹의 "가맹점 매출" placeholder도 이쪽 자리이므로 미터치.
- **첨부 후처리(미리보기/다운로드/삭제)** — 상세 첨부 영역(F717~F719)으로 ①소유. ⑤의 작성 폼은 **업로드 진입만**(권고: 상세에서 관리).
- **결재선 협조 결재자(`COOPERATOR`) 역할 지정 UI** — MVP 범위 밖(APPROVER 고정, ②③④선례).
- **테마/다크모드·다국어(i18n)·브라우저 푸시 알림** — 전 도메인 공통 제외.

### 기안서 상세 페이지 — 매출 본문 렌더·`[수정]` 진입 배선 (①소유 페이지에 ⑤ 배선 추가)

> **구현 기능:** (본문) `SalesDraftBody`(F701 슬롯 소비) · (배선) `F761` 진입 | **별도 페이지 아님**

- **매출 본문 렌더(`SalesDraftBody`)**: ①의 `DraftTypeBody`의 `draft.sales != null` "준비 중" 폴백(`TypeSlotFallback typeName="매출"`)을 실제 컴포넌트로 교체한다(④`LeaveDraftBody`와 동형 **read-only**). `sales` 슬롯(`franchiseName`·`reportMonth`·`salesAmount`)과 공통 `content`를 렌더. 매출액은 천 단위 구분(예: `1,000,000원`), 보고월은 dayjs 포맷. **참여자/공람 편집 뮤테이션 없음**(③출장 참여자 다이얼로그와 달리 매출 슬롯은 순수 표시 필드).

- **접근 권한**: 상세 페이지 자체는 ①소유(최소 요구 role `EMPLOYEE`, 조회 가능자=기안자/결재자/공람자). `[수정]` 버튼은 기안자 본인 + UNSUBMITTED에만 노출(①판정), 서버가 최종 판단(위반 시 403/도메인 에러 → `handleApiError` 토스트).

> **참고**: 로그인/회원가입/승인 대기, 공통 셸(헤더·사이드바·푸터), 문서함 4종·상세·워크플로우·첨부·결재대기함은 auth·shell·①공통 PRD 관할이며 여기서 재정의하지 않는다. 매출 기안 이력·결재 조회는 별도 페이지 없이 ①문서함 4종으로 커버된다.

## 🧩 FranchisePicker 설계 (F762 — 대상 가맹점 선택 UI, ⑤ 결정)

> `FRANCHISE_LIST`의 `managerId` 미검증·전체 검색 허용이라는 계약 사실(§권한 분기점) 위에서, ①`EmployeePicker`(제어형·다이얼로그 내 마운트·디바운스 검색·단일 페이지+검색 좁힘) 선례를 복제해 매출 폼 전용 단일 선택 위젯을 만든다. 아키텍처는 사용자 승인 완료(`features/franchise` 조회 슬라이스 + `features/approval` 소비 위젯).

- **위치·구조**: `features/franchise`(신규 얇은 슬라이스)에 조회 함수+훅 **하나만** — `getFranchises({ keyword?, status?, managerId?, page?, size? })`(①`getDepartments` 동형: 값 있는 파라미터만 조건부로 채워 전송, `Page<Franchise>` 반환) + `useFranchisesQuery`. 선택 위젯 `FranchisePicker`는 `features/approval/components`에 두고 `features/franchise` 훅을 cross-feature import(①`EmployeePicker`가 `features/department`를 소비하는 것과 동일 패턴).
- **선택 모델(제어형·단일 선택)**: `selected: { id: number; name: string } | null`, `onChange(next)`. 소비처(작성/수정 폼)가 선택 상태를 소유·유지하고 위젯은 탐색 UI·토글만 담당(수정 페이지는 프리필 `sales.{franchiseId,franchiseName}`로 초기 `selected` 구성).
- **기본 뷰 = 내 담당 가맹점 우선**: 마운트 시 `getFranchises({ managerId: 본인 empId })`로 담당 가맹점을 먼저 노출한다(본인 empId = `useMeQuery().data?.empBasicInfo.empId`, ①이 이미 확립한 기존 패턴 재사용). 서버가 담당 여부를 강제하지 않으므로 이는 **UX 편의**일 뿐 제약이 아니다.
- **검색 모드 = 전체 가맹점**: `keyword`(이름/주소) 입력 시 `managerId`를 빼고 전체 가맹점에서 검색(디바운스 300ms, ①`EmployeePicker`/DepartmentsPage 동일 값). 담당 외 가맹점도 선택 허용(서버가 임의 `franchiseId` 허용).
- **담당 0개 처리**: 기본 뷰 결과가 비면 빈 상태 안내("담당 가맹점이 없습니다. 이름·주소로 검색해 선택하세요") + 검색으로 전체 가맹점 선택 유도(fallback). 매출 기안 자체는 `FRANCHISE` role만 있으면 가능하므로 담당 0개여도 작성 차단하지 않는다.
- **페이징**: ①`EmployeePicker` 방식(넉넉한 단일 페이지 `size≈50` + `!last`면 "결과가 많습니다. 검색해 좁혀주세요" 안내). 과도한 제약·복잡한 페이지네이션은 MVP 밖(향후 가맹점 도메인 사이클).
- **status 필터**: MVP는 미노출(전체 상태 조회). 영업 상태별 기안 가능 여부는 서버 미제약이므로 프론트도 강제하지 않는다(Open Q#4). 목록 행에는 `BusinessStatus`(표시명)·`ownerName`·`address`를 보조 표기해 식별을 돕는다.

**계약 실측 메모:**
- **작성/수정 body 혼합 구조(⚠️ 평탄화 금지):** `param{title,content,approvers?}`는 ②일반 body와 동일 형태이나, 매출은 그 옆에 `franchiseId/reportMonth/salesAmount`가 **최상위 형제**로 붙는다(③출장의 `startAt/endAt/destination/purpose/participantIds`, ④연가의 `startAt/endAt/leaveType`와 동형 구조, 필드만 다름). `approvers` 항목 필드명은 `approverId`/`role`/`order` — 기존 `ApproverParam` 그대로.
- **`salesAmount` 도메인 규칙(백엔드 소스 실측):** `SalesDraft.validateSalesInitParam`가 `salesAmount > 0`을 state 검증한다("매출액은 마이너스가 될 수 없음" — 0 포함 이하 전부 거부). 백엔드 타입 `long`이므로 정수 → zod `.positive().int()`. 프론트 사전검증 후 서버 최종 판정.
- **`franchiseId` 담당 미검증(백엔드 소스 실측):** `SalesDraftService.findFranchise`는 `franchiseRepository.findById()`로 **존재 여부만** 확인하고 drafter의 담당 가맹점인지 검증하지 않는다. 서버는 임의 `franchiseId`를 허용하므로 프론트는 "내 담당 우선 노출 + 전체 검색 허용"으로 설계(§FranchisePicker).
- **`reportMonth` 형식:** 작성/수정 요청·상세 응답 모두 `"yyyy-MM"` 문자열(백엔드 `YearMonth`). 입력은 `<input type="month">`(값이 정확히 `yyyy-MM`)로 받아 그대로 전송, zod는 `/^\d{4}-(0[1-9]|1[0-2])$/` 또는 dayjs로 검증.
- **응답 코드:** 두 생성 API 모두 `201` + `{ draftId }` → 생성 후 `/approval/drafts/{draftId}` 상세 이동(②③④선례). 수정은 `204` Empty.
- **유형 판별(슬롯-null 규약):** 매출 기안 = `draft.sales != null`(`isSalesDraft`). ①의 `isGeneralDraft`(leave·businessTrip·sales·sourceDraftId 전부 null)와 동형 축. `draftType` 문자열 비교 금지.
- **첨부 정책(drafts 도메인):** 확장자/용량은 게시판 동일, **기안서당 최대 10개·총 10MB**(도메인모델). 위반 에러 `FILE_001~005`. 상세 정책은 `@../docs/도메인모델.md` 참조.

## ❓ Open Questions (계약 공백 — 개발 착수 전 확인 필요)

1. **상신 시 결재선 필수 검증 위치(②Open Q#1 계승).** `SALES_DRAFT_CREATE_SUBMISSION`의 `param.approvers`는 optional로 문서화되나 도메인 규칙은 "상신=결재자 ≥1"이다. 권고안: `[임시저장으로 생성]`은 결재선 없이 허용, `[생성 후 상신]`은 결재선 ≥1 클라 사전검증(②③④`CreatePage` 동일). 최종 판정 서버.
2. **`reportMonth` 중복/미래월 제약.** 백엔드 `validateSalesInitParam`은 `salesAmount > 0`만 검증하고 보고월 중복(같은 가맹점 같은 월 매출 기안 재작성)·미래월 제약은 소스에서 관측되지 않았다. 프론트는 제약 없이 서버 판정에 맡기는 것으로 가정 — 월 선택 UI에 미래월 제한/중복 사전 경고가 필요한지 확인.
3. **영업 상태(`status`)별 기안 가능 여부.** `franchiseId`는 존재만 검증하므로 폐업/영업중단 가맹점도 서버상 기안 가능하다. FranchisePicker에서 특정 `status`만 노출/선택 허용할지, 전체 노출 후 서버 판정에 맡길지 확인(현 설계: 전체 노출).
4. **매출 기안 첨부파일 범위(②③④ 계승).** 작성 폼에서 첨부 업로드(F716)를 포함할지 상세 첨부 영역(①)에서만 관리할지 확정 필요. 정책은 `@docs/backend-contract/file-upload.md` + `@../docs/도메인모델.md` 위임. 권고: ②③④선례대로 작성 폼은 첨부 없이 생성 → 상세에서 관리.
