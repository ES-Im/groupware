# 회의/회의실(Meeting) 예약·관리 Frontend MVP PRD

> 이 PRD는 신규 **meeting 도메인**의 두 관심사를 다룬다 — **①회의 예약(EMPLOYEE)**: 내 예약 캘린더·예약 가능 회의실 검색·예약 생성/수정/취소·참여자 교체·회의실 열람. **②회의·회의실 관리(FACILITY)**: 회의 예약 관리 목록·회의실 CRUD·활성화 토글·회의실 첨부(이미지) 업로드/삭제. 스코프는 `api-endpoint.md` 79~108행의 `SCHEDULE / MEETING API`(회의 예약 7종) + `MEETING ROOM API`(회의실 9종) + FILE API의 회의실 파일 4종(미리보기/다운로드/업로드/삭제), 총 **20개 엔드포인트**다.
>
> **범위 밖(명시적 제외)** — `SCHEDULE_CALENDAR`·`SCHEDULE_DETAIL`·`MANUAL_SCHEDULE_*`·`SCHEDULE_PARTICIPANTS_*`·`SCHEDULE_CANCEL`(수기/회의/출장/휴가를 아우르는 **통합 일정 캘린더**, api-endpoint.md 82~88행)는 별개의 크로스도메인 기능이며 이번 PRD 밖이다. 사이드바 "일정/회의" 그룹의 `일정 캘린더` placeholder는 그 자리이므로 **미터치**한다.
>
> **재구축 금지·소비만** — 아키텍처 배관(axios 인스턴스·`withCredentials`·QueryClient·`ProtectedRoute`·`hasRequiredRole`·LayoutShell·`handleApiError`·`useZodForm`/`submitWithErrorMapping`·shadcn 폼·sonner·dayjs)은 완성돼 있다. board 도메인이 확립한 **페이징 표준(@tanstack/react-table + Spring `Page` 메타, `number+1`)**, **파일 업로드/다운로드/미리보기 objectURL 표준**(board M11/M13), 전자결재가 확립한 **`EmployeePicker`(사원 선택 위젯, `features/department` 소비)**, franchise 도메인이 확립한 **Layer 2 역할 게이팅 선례**(FRANCHISE)를 **동형 복제**한다(내용 복제 아님, 패턴만). **`@fullcalendar/react`는 기술스택에 있으나 실제 소비 사례가 아직 없다 — 본 도메인의 내 예약 캘린더(F800)·회의실 예약 캘린더(F809)가 FullCalendar의 첫 소비처가 된다.**
>
> **전역 계약**(인증·reissue·401/403 분기·`ROLE_002`/`ROLE_003`·페이징 `number+1`·날짜 dayjs·`withCredentials`·ApiError `{code,name,httpStatus,message}`)은 CLAUDE.md §7 `BACK-END 계약 문서` 관할이며 여기서 재서술하지 않는다. 파일 정책은 도메인별로 다르므로 해당 페이지에 `@../docs/도메인모델.md` + `@docs/backend-contract/file-upload.md` 참조만 표기한다.

## 🎯 핵심 정보

- **목적**: 활성 사원이 예약 가능 회의실을 검색해 회의를 예약(제목·회의실·일시·참여자)하고, 내 예약을 캘린더로 확인·수정·취소하며, 시설 담당(FACILITY)이 전사 회의 예약을 관리하고 회의실 자원(정보·활성 상태·안내 이미지)을 등록/수정한다.
- **사용자**: 회의 예약·회의실 열람은 최소 요구 role `EMPLOYEE`(전 사원). 예약 수정/취소/참여자 교체는 **예약자 본인**(서버 최종 판정). 회의 예약 관리·회의실 CRUD/활성 토글/첨부 관리는 최소 요구 role `FACILITY`. `ADMIN`은 RoleHierarchy상 `FACILITY`를 자동 포함(메뉴·라우트 자동 접근). `FACILITY`는 `EMPLOYEE`를 포함하므로 예약 화면도 접근 가능.

## 🚶 사용자 여정

```
[비인증] → 로그인(리디렉션, auth 관할) → 세션 복원(부팅 시 reissue 1회 · 본인정보 GET /api/employees/me)

[사이드바 "일정/회의 > 회의실 예약"] (minRole EMPLOYEE) → 내 회의 예약 캘린더(P1)
  ├ 캘린더 이벤트 클릭 → 회의 예약 상세(P3)
  │     └ (예약자 본인) 예약 정보 수정 / 참여자 교체 / 예약 취소
  └ [회의 예약하기] → 회의 예약 생성(P2)
        ├ 날짜·시작/종료 시각·최소 수용인원 입력 → 예약 가능 회의실 검색(F802)
        ├ 회의실 카드 [상세 보기] → 회의실 상세·안내 이미지·해당 회의실 예약 캘린더 열람(P4)
        └ 회의실 선택 + 제목 + 참여자 지정(EmployeePicker) → [예약] → 성공 시 내 예약 캘린더(P1)

[사이드바 "일정/회의 > 회의 예약 관리"] (minRole FACILITY) → 회의 예약 관리 목록(P5)
  └ 행 클릭 → 회의 예약 상세(P3, FACILITY는 조회 전용 — 수정/취소 버튼 미노출)

[사이드바 "일정/회의 > 회의실 관리"] (minRole FACILITY) → 회의실 관리 목록(P6)
  ├ [회의실 등록] 다이얼로그 → 생성(F812) → 목록 갱신
  ├ 행 [활성화/비활성화] 토글(F814)
  └ 행 클릭 → 회의실 관리 상세(P7) → 정보 수정(F813) / 안내 이미지 업로드(F815)·삭제(F816) / 활성 토글(F814)
```

**권한 분기점**

- 라우트 가드(Layer 1): 미인증 → 로그인 리디렉션(auth 관할). 예약 계열 라우트는 최소 요구 role `EMPLOYEE`, 관리 계열 라우트는 최소 요구 role `FACILITY`(security.md 36행: `GET /api/meetings`·`/api/meeting-rooms/management`·`/api/meeting-rooms/**`(POST/PATCH/DELETE) → `FACILITY`). `hasRequiredRole`로 사이드바·라우트 게이팅, 서버가 최종 판단.
- 서버 최종 판단(role 아닌 문서-사원 관계·도메인 규칙):
  - **예약 수정/참여자 교체/취소**(F804/F805/F806)는 **예약자 본인**만(서버 판정). 타인 시도 시 403 → 권한 부족 UX(재발급 금지). 이 소유자 불일치는 부서 불일치(`ROLE_003`)와 다른 도메인 에러코드이므로 프론트는 `code` 비의존으로 `handleApiError` 토스트 처리하고 상세로 복귀시킨다.
  - **회의 수정 가능 기간**: 회의일 **1일 전까지만** 수정 가능, **취소된 회의는 수정 불가**(도메인모델). 프론트는 이 규칙을 버튼 노출 힌트(예약자 본인 + `isCanceled=false` + 회의일이 내일 이후)로만 쓰고, 최종 판정은 서버(위반 시 도메인 에러 토스트).
  - **참여자 교체는 회의 타입 일정만**(도메인모델). 본 도메인의 회의 예약은 전부 회의 타입이므로 F805가 항상 유효.
  - **회의실 이름 유일성·수용인원 ≥1**(도메인모델): 프론트는 zod 사전검증(공백불가·양수)하고 이름 중복은 서버 판정(도메인 에러 토스트).
  - **회의실 첨부(이미지) 제약**: 이미지 전용·용량 상한은 서버 최종 판정(에러 `FILE_001~005`). ⚠️ 상한값이 문서 간 상이 → **Open Q#3**. 정책 원천은 `@docs/backend-contract/file-upload.md`.

### 4. MVP 필수 지원 기능 — 신규 기능ID 없음(전역 자산 소비)

- **로그인 + 세션 복원 + 회원가입/승인 대기** — auth·shell PRD 관할(`LOGIN`/`REISSUE_TOKEN`/`RETRIEVE_ME_INFO`/`REGISTER`). 본 도메인은 진입 전제로만 사용하며 재구현하지 않는다.
- **본인 empId 획득** — 예약 생성 `reserverId`·"내 예약" 판정·예약자 본인 액션 노출에 `useMeQuery().data?.empBasicInfo.empId`(전자결재가 확립한 기존 패턴)를 재사용. 로딩 전/부재 시 `undefined` → fail-closed(예약자 액션 미노출).
- **참여자 선택 위젯** — F803 생성·F805 교체의 참여자 지정에 전자결재 `EmployeePicker`(다중 선택, `features/department` 소비)를 재사용. **참여자 풀은 전사 전체 검색**(부서 한정 아님), **예약자(`reserverId`)와 참여자(`participants`)는 별개로 취급**(예약자 자동 포함 안 함 — 확정, 사용자 결정 2026-07-10).
- **페이징 표(react-table)·파일 objectURL 유틸** — board 도메인 표준을 F810/F811(표), F808/F815(파일)에서 소비.

### 5. MVP 이후 기능 / 범위 외 (이번 PRD 명시적 제외)

- **통합 일정 캘린더**(`SCHEDULE_CALENDAR`·`SCHEDULE_DETAIL`·`MANUAL_SCHEDULE_*`·`SCHEDULE_PARTICIPANTS_*`·`SCHEDULE_CANCEL`) — 수기/회의/출장/휴가 통합 뷰, 별개 크로스도메인 기능. 사이드바 `일정 캘린더` placeholder 미터치.
- **회의실 변경 전용 API** — 존재하지 않음. 도메인모델상 회의실 변경은 "취소(F806) 후 재예약(F803)"으로 처리(Open Q#2와 연동).
- **회의 예약에 대한 FACILITY의 강제 취소/수정** — 계약상 예약 수정/취소는 예약자 본인만. FACILITY는 관리 목록·상세 **조회 전용**(별도 관리자 취소 API 부재).
- **테마/다크모드·다국어(i18n)·브라우저 푸시 알림** — 전 도메인 공통 제외.

## 📱 메뉴 구조

```
📱 HARUON 내비게이션
└── 📁 일정/회의 (그룹 · 기존, minRole: EMPLOYEE) — sidebarMenuItems.ts "일정/회의"
     ├── 일정 캘린더 — (placeholder 유지, 범위 밖 · 미터치)
     ├── 회의실 예약 — F800(진입) · F801~F809 (minRole: EMPLOYEE)   ← 기존 placeholder를 실 라우트로 승격
     ├── 회의 예약 관리 — F810 (minRole: FACILITY)                  ← 신규 항목(ADMIN 자동 포함)
     └── 회의실 관리 — F811(진입) · F812~F816 (minRole: FACILITY)   ← 기존 placeholder를 실 라우트로 승격
```

- **"회의실 예약"**(min `EMPLOYEE`) → 내 회의 예약 캘린더(P1) 랜딩. 여기서 예약 생성(P2)·상세(P3)·회의실 열람(P4)으로 전개. 기존 `{ label: '회의실 예약', minRole: 'EMPLOYEE', implemented: false }` placeholder를 `to` 부여 + `implemented` 제거로 승격.
- **"회의실 관리"**(min `FACILITY`) → 회의실 관리 목록(P6) 랜딩. 기존 `{ label: '회의실 관리', minRole: 'FACILITY', implemented: false }` placeholder 승격. `hasRequiredRole('FACILITY')`가 비FACILITY에게 미노출, `ADMIN` 자동 포함(상위 role 병기 불필요) — franchise 그룹(FRANCHISE 게이팅) 선례 동형.
- **"회의 예약 관리"**(min `FACILITY`) → 회의 예약 관리(P5). **기존 placeholder에 없던 신규 메뉴 항목**을 이 그룹에 추가한다(회의실 자원 관리와 회의 예약 감독은 별개 관심사라 분리). `MEETING_RESERVATION_MANAGEMENT`(FACILITY)의 유일한 진입점.
- **DEPT_MANAGER 전용 항목 없음**(본 도메인은 "같은 부서" 조건 무관). Layer 1은 `EMPLOYEE` 라우트 가드, Layer 2는 `FACILITY` 메뉴·라우트 노출에 사용.

**계약 실측 메모:**

- **시각 포맷 불일치(⚠️):** `MEETING_RESERVATION_CREATE` request-fields는 `startAt`/`endAt`를 **`HH:mm`**로 문서화하나, request-body 예시는 **`"10:00:00"`(HH:mm:ss)**로 표기된다. `AVAILABLE_MEETING_ROOMS`·`MEETING_ROOM_RESERVATIONS_CALENDAR` 쿼리·응답은 `HH:mm`/`HH:mm:ss`가 혼재. → **Open Q#5**. 착수 전 전송 포맷 확정 필요(권고: field 스펙대로 `HH:mm` 전송, 응답은 `HH:mm:ss`도 파싱 가능하게 dayjs 처리).
- **날짜/기간 파라미터:** 캘린더 조회(`start`/`end`)는 `yyyy-MM-dd'T'HH:mm:ss`(포함/미포함, 미입력 시 당월 1일 0시 ~ 익월 1일 0시). 회의일(`meetingDate`)·검색 날짜(`date`)는 `yyyy-MM-dd`. 관리 목록 월 필터(`yearMonth`)는 `yyyy-MM`. 전부 dayjs로 조립.
- **회의실 예약 캘린더 필드 축소(설계 의도):** `MEETING_ROOM_RESERVATIONS_CALENDAR`는 `meetingId`·`title`을 **의도적으로 내려주지 않는다**(예약자 부서/이름·참여자수·일시만). 타 부서 예약의 세부를 감추고 "점유 시간대"만 노출하는 용도 → 이 캘린더 이벤트는 상세(P3)로 링크하지 않는다.
- **회의실 이름 길이:** `MEETING_ROOM_CREATE`/`UPDATE` request-fields 기준 **≤50자**·공백불가(도메인모델의 "유일성"은 서버 판정). 수용인원은 양수(≥1).
- **표준 페이지 메타:** F810/F811 응답은 `content` + `totalElements`/`totalPages`/`number`/`size`/`numberOfElements`/`first`/`last`/`empty`(Spring Page). UI 페이지 번호는 `number+1`.
- **응답 코드:** 조회 `200`, 회의실 등록 `201 {meetingRoomId}`, **회의 예약 생성 `201` Empty(본문 없음 — draftId류 반환 없음)**, 수정/취소/토글/파일 `204`.

## ❓ Open Questions — 확정 내역 (검증·사용자 확인 완료, 2026-07-10)

> `groupware-prd-validator` 검증(non-minor 이슈 0건) + 사용자 확인을 거쳐 전부 해소됨. 개발 착수 시 아래 확정안을 그대로 구현한다.

1. **참여자 선택 소스·예약자 자동 포함 — 확정.** 참여자 풀은 **전사 전체 검색**(부서 한정 아님) — `EmployeePicker`(`features/department`=`DEPT_MEMBERS` 소비 위젯)를 전사 검색 모드로 재사용. **예약자(`reserverId`)와 참여자(`participants`)는 별개로 취급**(예약자 자동 포함 안 함).
2. **회의실 변경 UX — 확정: 필드 노출.** `MEETING_RESERVATION_UPDATE`의 `meetingRoomId`(optional) 필드를 **수정 다이얼로그에 노출**한다(서버가 허용하는 대로, PRD 최초 권고였던 "취소+재예약 유도" 대신 채택). 회의실 변경 시 새 회의실·시간대의 가용 여부는 서버가 최종 판단(충돌 시 도메인 에러 토스트로 처리, 프론트 사전검증 없음).
3. **회의실 첨부 상한·확장자 불일치 — 해소됨(검증 확인).** CLAUDE.md §7이 `file-upload.md`를 파일 정책 원천으로 지정 → **10MB·jpg/jpeg/png 채택**(gif 불가). 프론트 `accept="image/jpeg,image/png"`.
4. **FACILITY의 회의 예약 개입 범위 — 확정: 조회 전용.** 계약상 예약 수정/취소는 예약자 본인만이며 FACILITY 강제 취소 API가 부재(계약 확인됨) → 회의 예약 관리(P5)는 **조회 전용**으로 확정, 액션 버튼 없음.
5. **시각 전송 포맷(HH:mm vs HH:mm:ss) — 해소됨(검증 확인).** 필드 스펙(권위) 기준 **`HH:mm` 전송**, 응답은 `HH:mm:ss`도 파싱 가능하게 dayjs 처리.
6. **예약 생성 시 capacity 자동 산정 — 계약 이슈 아님(검증 확인).** capacity 필수 입력은 확정. UX 순서는 PRD 설계 그대로: 인원 먼저 입력 → 회의실 검색 → 참여자 지정, 참여자 수 > capacity 시 프론트 경고만 표시(서버 강제 아님).
