# 가맹점(Franchise) 관리·교육·문의·매출 Frontend MVP PRD

> 이 PRD는 신규 **franchise 도메인**의 네 관심사를 다룬다 — **①가맹점 관리**: 목록·검색·등록·상세·기본정보 수정·영업상태 변경·담당자 변경·메모. **②가맹점 교육**: 교육 캘린더·상세·신청자·등록·수정·활성/비활성·첨부(문서형) 업로드/삭제/미리보기/다운로드. **③가맹점 문의**: 문의 목록·상세·답변 조회·담당자 배정·답변 초안 생성/수정·답변 발송. **④가맹점 매출 조회**: 연/월/일 매출을 읽기 전용으로 조회·시각화. 스코프는 `api-endpoint.md` 190~217행의 `FRANCHISE API` 25종 + FILE API의 교육 파일 4종(`EDUCATION_FILE_UPLOAD`/`DELETE`/`PREVIEW`/`DOWNLOAD`, 230~231·238·244행), 총 **29개 엔드포인트**다.
>
> **범위 밖(명시적 제외)** — **매출 기안서(`SALES_DRAFT_*`)는 이번 PRD 밖이다.** 매출 기안 작성/수정/상신은 이미 **approval 도메인**(`src/features/approval/pages/SalesDraft*`)에 구현 완료됐다. franchise 도메인은 **매출 "조회"(`FRANCHISE_SALES_*`)만** 다룬다. 다만 매출 데이터의 원천-소비 도메인 관계는 §🔗에 명시한다.
>
> **재구축 금지·소비/확장만** — 아키텍처 배관(axios 인스턴스·`withCredentials`·reissue 인터셉터·QueryClient·`ProtectedRoute`·`hasRequiredRole`·LayoutShell·sidebarMenuItems·`handleApiError`·`useZodForm`/`submitWithErrorMapping`·shadcn 폼·sonner·dayjs·페이징 파서)은 완성돼 있다. board가 확립한 **페이징 표준(@tanstack/react-table + Spring `Page` 메타, `number+1`)**, board M11/M13이 확립한 **파일 업로드/다운로드/미리보기 objectURL 표준**, 전자결재·쪽지가 확립한 **`EmployeePicker`(사원 선택 위젯, 현재 `src/shared/components/EmployeePicker.tsx`로 승격 완료)**, meeting이 확립한 **`@fullcalendar/react` 소비 선례**, meeting/company가 확립한 **Layer 2 역할 게이팅(FACILITY/ADMIN 전용 메뉴)** 을 **동형 복제**한다(패턴만, 내용 복제 아님). 이미 존재하는 franchise 스캐폴딩(`src/features/franchise/api/getFranchises.ts`·`useFranchisesQuery.ts`·`getFranchiseMonthlySales.ts`·`model/franchise.ts`·`model/queryKeys.ts` — 매출 기안서 작업 때 생성)과 approval의 `FranchisePicker`(가맹점 선택 위젯)를 **소비·확장**한다.
>
> **전역 계약**(인증·부팅 시 `reissue` 1회·401/403 분기·`ROLE_002`/`ROLE_003`·페이징 `Page` 구조/`number` 0-based·날짜 dayjs·`withCredentials`·`ApiError {code,name,httpStatus,message}`)은 CLAUDE.md §7 `BACK-END 계약 문서` 관할이며 여기서 재서술하지 않는다. 파일 정책은 도메인별로 다르므로 해당 페이지에 `@../docs/도메인모델.md` + `@docs/backend-contract/file-upload.md` 참조만 표기한다.

## 🎯 핵심 정보

- **목적**: 가맹 본사 담당자가 **가맹점**을 등록·검색·관리(기본정보·영업상태·담당자·메모)하고, **가맹점 교육**을 캘린더로 편성(등록·수정·활성/비활성·첨부·신청자 확인)하며, **가맹점 문의**를 접수·배정·답변(초안 작성/수정/발송)하고, 가맹점별 **매출**을 연/월/일 단위로 조회·시각화한다.
- **사용자**: 전 기능 최소 요구 role `FRANCHISE`(Layer 2 업무 권한). `ADMIN`은 RoleHierarchy상 `FRANCHISE`를 자동 포함하므로 메뉴·라우트·기능 전부 자동 접근한다(security.md 18행). `FRANCHISE`는 `EMPLOYEE`를 포함하므로 로그인·공통 셸 접근에는 문제없다. **일부 기능은 role 위에 소유자/상태 조건이 겹친다** — 교육 수정·활성토글·첨부(교육 등록자 + 비활성·신청자 0 상태), 문의 답변 생성/수정/발송(답변 담당자) — 이는 role이 아니라 서버가 최종 판정한다(§권한 분기점).

## 🚶 사용자 여정

```
[비인증] → 로그인(리디렉션, auth 관할) → 세션 복원(부팅 시 reissue 1회 · 본인정보 GET /api/employees/me)

[사이드바 "가맹점 > 가맹점 관리"] (minRole FRANCHISE) → 가맹점 목록(P1)
  ├ [가맹점 등록] 다이얼로그 → 생성(F1603) → 목록 갱신
  └ 행 클릭 → 가맹점 상세(P2)
        ├ 기본정보 수정(F1604) / 영업상태 변경(F1605) / 담당자 변경(F1606, EmployeePicker 단일) / 메모 수정·삭제(F1607·F1608)
        └ [매출 조회] → 가맹점 매출 조회(P3, franchiseId 프리필)

[사이드바 "가맹점 > 가맹점 매출"] (minRole FRANCHISE) → 가맹점 매출 조회(P3)
  └ 가맹점 선택(FranchisePicker) + 기간(연/월/일) → 연 매출(F1624)·월 매출(F1625)·일 매출(F1626) 조회·시각화

[사이드바 "가맹점 > 가맹점 교육"] (minRole FRANCHISE) → 교육 캘린더(P4)
  ├ [교육 등록] 다이얼로그 → 생성(F1612, 비활성 상태로 생성) → 생성된 교육 상세로 이동
  └ 이벤트 클릭 → 교육 상세(P5)
        ├ (등록자·비활성·신청자 0) 교육 수정(F1613)
        ├ 활성화/비활성화(F1614) · 첨부 업로드/삭제(F1615)·미리보기/다운로드(F1616)
        └ 신청자 목록(F1611, 페이징 표)

[사이드바 "가맹점 > 가맹점 문의"] (minRole FRANCHISE) → 문의 목록(P6)
  └ 행 클릭 → 문의 상세(P7)
        ├ 답변 담당자 배정(F1620, EmployeePicker 단일)
        └ (답변 담당자) 답변 조회(F1619) → 초안 생성(F1621)/수정(F1622) → 발송(F1623)
```

**권한 분기점**

- **라우트 가드(Layer 1)**: 미인증 → 로그인 리디렉션(auth 관할). franchise 계열 라우트는 다른 도메인 컨벤션과 동일하게 **`ProtectedRoute`(인증 가드)만** 적용하고(라우트 자체엔 role 가드 미부착), **Layer 2 게이팅은 사이드바 `hasRequiredRole('FRANCHISE')`** 로 처리한다(meeting의 FACILITY, company의 ADMIN 선례 동형). 최종 권한은 서버 403이 판단 — 직접 URL 진입한 비FRANCHISE에게는 서버가 403을 반환하고 프론트는 권한 부족 UX로 처리(재발급 금지).
- **서버 최종 판단(role 아닌 소유·상태 조건)**:
  - **교육 수정/활성토글/첨부**(F1613/F1614/F1615)는 **교육 등록자**(ADMIN 소유자 조건)만(api-endpoint.md 205~207·238·244행 "교육 등록자"). 단, `FRANCHISE_EDUCATION_DETAIL` 응답에 등록자 식별자 필드가 없어(스니펫 실측, Open Q#6) 프론트에서 등록자 비교가 불가하다 — **등록자 판정은 서버 403 전담**, 프론트는 `isActive`/`appliedCount` 상태 힌트만 제공.
  - **교육 수정 가능 상태**(도메인모델): "비활성 상태에서만 수정 가능" + "신청 정보가 하나라도 존재하면 수정 불가". 프론트는 `isActive=false && appliedCount=0`을 수정 버튼 노출 힌트로만 쓰고, 위반 시 서버 도메인 에러 토스트.
  - **문의 답변 생성/수정/발송**(F1621/F1622/F1623)은 **답변 담당자**만(도메인모델 "답변의 수정이나 제출은 문의 담당자만"). 프론트 힌트: `inquiryDetail.assignedManagerId === myEmpId`. 담당자 미배정 문의는 답변 불가 → 먼저 배정(F1620) 유도.
  - 이 소유자/상태 불일치 403은 **부서 불일치(`ROLE_003`)와 다른 도메인 에러코드**이므로 프론트는 `code` 비의존으로 `handleApiError` 토스트 처리하고 원 화면으로 복귀시킨다.

### 5. MVP 필수 지원 기능 — 신규 기능ID 없음(전역 자산 소비)

- **로그인 + 세션 복원 + 회원가입/승인 대기** — auth·shell PRD 관할(`LOGIN`/`REISSUE_TOKEN`/`RETRIEVE_ME_INFO`/`REGISTER`). 본 도메인은 진입 전제로만 사용하며 재구현하지 않는다.
- **본인 empId 획득** — 교육 등록자 판정·답변 담당자 판정(액션 버튼 노출 힌트)에 `useMeQuery().data?.empBasicInfo.empId`(기존 패턴)를 재사용. 로딩 전/부재 시 `undefined` → fail-closed(소유자 액션 미노출).
- **사원 선택 위젯** — 담당자 변경(F1606)·답변 담당자 배정(F1620)의 사원 지정에 `EmployeePicker`(현 `src/shared/components/EmployeePicker.tsx`, **단일 선택 모드**)를 재사용. 신규 사원검색 API 발명 금지. 서버가 활성·권한 검증을 최종 수행.
- **가맹점 선택 위젯** — 매출 조회(P3)의 가맹점 선택에 approval의 **`FranchisePicker`**(`src/features/approval/components/FranchisePicker.tsx`, `FRANCHISE_LIST` 소비)를 재사용/확장. franchise 도메인으로의 공용화 위치는 **Open Q#4**.
- **페이징 표(react-table)·파일 objectURL 유틸** — board 표준을 F1601/F1611/F1617(표), F1615/F1616(파일)에서 소비.

### 6. MVP 이후 기능 / 범위 외 (이번 PRD 명시적 제외)

- **매출 기안서(`SALES_DRAFT_CREATE`/`UPDATE`/`SUBMISSION` 등)** — approval 도메인에 구현 완료. franchise 도메인은 매출 **조회**만. (§🔗 원천-소비 관계 참조)
- **가맹점 외부 API 싱크(`Franchise_sync_request`, 일매출/문의/교육신청 배치)** — 백엔드 배치 관할, 프론트 화면 없음(도메인모델). 매출·문의·신청 데이터는 이 싱크로 생성되며 프론트는 결과만 조회.
- **가맹점 삭제·문의 원문 수정/삭제** — 가맹점 삭제 엔드포인트 부재(영업상태 `CLOSE`로 대체), 문의 원문은 외부 싱크 소유(프론트 수정 불가, `isDeleted` 플래그만 표시).
- **테마/다크모드·다국어(i18n)·브라우저 푸시 알림** — 전 도메인 공통 제외.

## 🔗 매출 데이터 원천-소비 도메인 관계 (명시)

- **franchise 도메인의 매출 조회(F1624~F1626)는 읽기 전용 리포팅**이다. 매출 원천 데이터(`Franchise_daily_sales`)는 이 도메인 밖에서 생성된다.
- **approval 도메인의 매출 기안서**는 별개의(이미 구현된) 흐름으로, `FRANCHISE`가 월 매출을 보고·상신한다. 매출 기안 작성 폼의 `[매출액 불러오기]`가 **`FRANCHISE_SALES_MONTHLY`(F1625)의 `totalSalesAmount`를 소비**해 기안 금액을 프리필한다(스캐폴딩 `getFranchiseMonthlySales.ts` 주석 실측). 즉 **매출 조회가 소스, 매출 기안서가 소비자**다.
- ⚠️ 팀 지시("매출 데이터 생성 경로 = 매출 기안서 결재 완료")와 계약 증거(도메인모델: 일매출은 외부 API 싱크 `DAILY_SALES`로 생성 / 스캐폴딩: 기안서가 조회를 소비)가 **방향이 상충**한다. 권위 있는 쓰기 경로 확정은 **Open Q#1**로 남긴다. 어느 쪽이든 franchise 도메인의 매출 조회 화면 구현에는 영향이 없다(읽기 전용).

```
📱 HARUON 내비게이션
└── 👥 가맹점 (Layer 2 업무 그룹 · minRole: FRANCHISE) — sidebarMenuItems.ts "가맹점" 그룹(기존 placeholder)
     ├── 가맹점 관리 — F1601(진입) · F1602~F1608 (minRole: FRANCHISE)   ← 기존 placeholder 승격
     ├── 가맹점 교육 — F1609(진입) · F1610~F1616 (minRole: FRANCHISE)   ← 기존 placeholder 승격
     ├── 가맹점 문의 — F1617(진입) · F1618~F1623 (minRole: FRANCHISE)   ← 기존 placeholder 승격
     └── 가맹점 매출 — F1624~F1626 (minRole: FRANCHISE)                ← 기존 placeholder 승격
```

- 사이드바 `가맹점` 그룹(minRole `FRANCHISE`)과 그 4개 자식(`가맹점 관리`/`가맹점 교육`/`가맹점 문의`/`가맹점 매출`)은 **이미 `src/shared/components/sidebarMenuItems.ts:157-167`에 placeholder(`implemented:false`)로 존재**한다(자식 4개 162~165행). 각 항목에 `to`(라우트)를 부여하고 `implemented` 플래그를 제거해 **실 라우트로 승격**한다.
- `hasRequiredRole('FRANCHISE')`가 비FRANCHISE에게 그룹 전체를 미노출한다. **`ADMIN`은 RoleHierarchy상 `FRANCHISE`를 자동 포함**하므로 상위 role 병기 불필요 — 별도 ADMIN 전용 섹션 불필요(meeting FACILITY 그룹·company ADMIN 그룹 선례 동형).
- **DEPT_MANAGER 전용 항목 없음**(가맹점은 부서 스코프 무관, Layer 2 도메인). Layer 1은 라우트 인증 가드, Layer 2 `FRANCHISE`는 메뉴·라우트 노출에 사용.

**계약 실측 메모:**

- **식별자 필드 상이(⚠️):** 목록·상세 응답은 `id`, 생성 응답은 `franchiseId`, 교육은 `id`/`educationId`, 문의는 `inquiryId`, 답변은 `answerId`로 엔드포인트마다 키가 다르다. 프론트 타입은 스니펫 실측대로 유지(스캐폴딩 `franchise.ts`가 목록 `id`를 이미 채택).
- **영업상태 표시명 vs enum 코드:** `FRANCHISE_LIST`/`DETAIL` 응답의 `BusinessStatus`는 **한글 표시명 문자열**(스캐폴딩 주석 실측: `"정상 영업 중"`류)이나, `FRANCHISE_STATUS_UPDATE`·`FRANCHISE_LIST` 필터의 `status`는 **enum 코드**(`OPEN` 등)다. 조회는 표시명, 전송은 코드로 분리 취급.
- **매출 숫자 날짜 포맷:** 응답의 `salesMonth`(`yyyyMM`)·`salesDate`(`yyyyMMdd`)는 **문자열이 아닌 숫자**다(스캐폴딩 실측). 요청 경로의 `yyyy-MM`/`yyyy-MM-dd`와 형식이 다르므로 축/라벨 표기 시 dayjs 파싱 주의. 단, `FRANCHISE_SALES_DAILY` 응답의 `salesDate`는 `String`(response-fields 실측) — 연/월 매출과 타입이 다름.
- **교육 첨부 경로:** 교육 CRUD는 `/api/franchise-educations/**`이나 교육 **파일**은 `/api/educations/{educationId}/files/**`(prefix 상이). api-endpoint.md 230~231·238·244행 실측.
- **교육 활성 토글 메서드:** 활성/비활성은 `POST`(회의실 토글의 `PATCH`와 다름). 스니펫 http-request 실측.
- **표준 페이지 메타:** F1601/F1611/F1617 응답은 `content` + `totalElements`/`totalPages`/`number`/`size`/`numberOfElements`/`first`/`last`/`empty`(Spring Page). UI 페이지 번호 `number+1`.
- **응답 코드:** 조회 `200`, 가맹점·교육 생성 `201 {franchiseId|educationId}`, **문의 답변 생성 `201` Empty**, 나머지 수정·상태·담당자·메모·활성토글·발송·파일 `204`.
