# 인사관리 — 신규 사원 가입승인 + 조직소속 배정 Frontend MVP PRD

> 이 PRD는 **인사관리 도메인의 워킹 스켈레톤**을 다룬다 — HR/ADMIN이 **가입대기자(status=PENDING) 목록을 조회**하고, 특정 대기자를 **가입 승인(PENDING→ACTIVE)** 한 뒤, **같은 플로우 안에서 이어서 조직소속(부서/직급/주요소속/발령시작일)을 최초 배정**하는 3단계 흐름이다. 스코프는 `api-endpoint.md` EMP_ACCOUNT 섹션(20~44행)의 **3개 엔드포인트**(`NEW_EMP_LIST`·`HR_APPROVE_EMP_REGISTRATION`·`HR_UPDATE_EMP_BELONGINGS`)와, 부서 선택용 **기존** `DEPTS`(재사용)다.
>
> **범위 밖(명시적 제외).** 사원 개인정보 수정(`HR_UPDATE_EMP_INFO`·`UPDATE_SELF_INFO`), 퇴직/정직/활성화(`HR_RESIGN_EMP`·`HR_SUSPEND_EMP`·`HR_ACTIVATE_EMP`), 사원 파일 관리, **기존(현재) 소속 수정**(`HR_UPDATE_EMP_BELONGINGS`의 `deptId=null` 케이스), 관리용 사원 목록(`EMPS_FOR_MANAGEMENT`) 등 EmpManagementApi의 다른 기능은 이번 PRD 밖이다(별도 PRD/향후 사원 관리 화면 소관). **가입 승인 거부·반려 기능은 백엔드에 대응 엔드포인트가 없어 발명하지 않는다.**
>
> **재구축 금지·소비만** — 아키텍처 배관(axios `withCredentials`·QueryClient·`ProtectedRoute`·`hasRequiredRole`·LayoutShell·`handleApiError`·`useZodForm`/`submitWithErrorMapping`·shadcn 폼·sonner·dayjs)은 완성돼 있다. **부서 선택 드롭다운은 `features/department`의 `useDepartmentsQuery`(`DEPTS`)를 그대로 소비**한다(새 조회 훅 생성 금지). 페이징 테이블은 부서 멤버/관리용 사원 목록이 확립한 `@tanstack/react-table` + Spring `Page<T>` 소비 표준을 동형 재사용한다.
>
> **전역 계약**(인증·reissue·401/403 분기·`ROLE_002`/`ROLE_003`·`ApiError {code,name,httpStatus,message}`·날짜 dayjs·페이징 구조·`withCredentials`)은 CLAUDE.md §7 `BACK-END 계약 문서` 관할이며 여기서 재서술하지 않는다.
>
> **UI 범위 노트** — 본 PRD 단계는 **최소 기능 뷰만 배치**한다. 시각 스타일 다듬기(Ubold 톤 이식 등)는 이후 `adapt-ui`/`ux-ui-stylist` 단계 몫이다.

## 🎯 핵심 정보

- **목적**: HR/ADMIN이 신규 가입 신청자를 승인하고, 승인 직후 이어서 조직소속(부서·직급·주요소속·발령시작일)을 최초 배정해 정식 재직 사원으로 편입시킨다.
- **사용자**: 최소 요구 role **`HR`**(Layer 2 업무 권한). RoleHierarchy상 `ADMIN`은 자동 포함. `DEPT_MANAGER`·일반 `EMPLOYEE`는 접근 불가(HR은 Layer 2라 Layer 1 상위 등급이 자동 포함하지 않음 — ADMIN만 포함).

## 🚶 사용자 여정

```
[비인증] → 로그인(리디렉션, auth 관할) → 세션 복원(부팅 시 reissue 1회 · 본인정보 GET /api/employees/me)

[사이드바 "인사관리 > 신규 사원 승인"] (minRole HR) → 신규 사원 승인 페이지(P1)
  ├ 이름 검색 / 페이지 이동 → 가입대기자(PENDING) 목록 재조회
  └ 특정 대기자의 [승인] 클릭 → 승인 마법사 다이얼로그(P2)
        ├ 1단계: 입사일자 입력 → [승인] → HR_APPROVE_EMP_REGISTRATION(204, PENDING→ACTIVE)
        │        성공 시 자동으로 2단계로 전진(승인은 되돌릴 수 없음)
        └ 2단계: 부서·직급·주요소속·발령시작일 입력 → [소속 배정 완료]
                 → HR_UPDATE_EMP_BELONGINGS(204) → 다이얼로그 닫고 목록 갱신(P1)

[비HR·비ADMIN이 URL 직접 진입] → 라우트 가드가 접근 차단(권한 부족 UX / 홈 리디렉션)
```

**권한 분기점**

- 라우트 가드(role): 미인증 → 로그인 리디렉션(auth 관할). 인사관리 라우트는 최소 요구 role `HR`(api-endpoint.md 36~38행: 3개 엔드포인트 전부 "HR 또는 ADMIN"). `ADMIN`은 RoleHierarchy상 자동 포함. `DEPT_MANAGER`·`EMPLOYEE`는 미포함 → 접근 불가.
- **순서 강제(도메인 규칙)**: 소속 배정(`HR_UPDATE_EMP_BELONGINGS`)은 대상 사원이 `ACTIVE`일 때만 가능하다. 따라서 **승인(1단계) → 소속배정(2단계) 순서로만** 진행되며 역순은 불가능하다. 프론트는 이 순서를 마법사 단계 전이로 강제한다(2단계는 1단계 승인 성공 이후에만 도달).
- 서버 최종 판단은 **role(HR/ADMIN)뿐**이며 "같은 부서" 같은 관계 조건이 없다 → `ROLE_003`(부서 불일치) 경로는 이 도메인에 해당 없음.

## ⚡ 기능 명세

### 1. MVP 핵심 기능

| ID | 기능명 | 설명 | 근거 기능ID | 관련 페이지 |
|---|---|---|---|---|
| **[F001]** | 가입대기자 목록 조회 | status=PENDING 신규 사원을 **페이징** 조회하고 **사원 이름(keyword)** 으로 검색. 각 행에 사원번호·이름·로그인ID·이메일·내선번호 표시, 행별 `[승인]` 액션. keyword 미입력 시 전체 PENDING 조회 | `NEW_EMP_LIST` | 신규 사원 승인 페이지 |
| **[F002]** | 가입 승인 | 대상 사원의 **입사일자(hiredAt, yyyy-MM-dd)** 를 지정해 승인(PENDING→ACTIVE). 요청 바디 없음(hiredAt은 쿼리). `204`. 성공 시 마법사 2단계(소속 배정)로 자동 전진 | `HR_APPROVE_EMP_REGISTRATION` | 승인 마법사 다이얼로그(1단계) |
| **[F003]** | 조직 소속 최초 배정 | 승인된(ACTIVE) 사원에게 **부서·직급·주요소속여부·발령시작일**을 지정해 최초 소속을 등록. 신규 소속 등록이므로 `deptId`·`position`·`isPrimary`·`startAt` **4개 모두 필수**, `endAt`은 미수집(null=현재 진행 소속). `204`. 성공 시 다이얼로그 닫고 목록 갱신 | `HR_UPDATE_EMP_BELONGINGS` | 승인 마법사 다이얼로그(2단계) |

### 2. MVP 필수 지원 기능 — 신규 기능ID 없음(전역/기존 자산 소비)

- **부서 선택 목록** — 소속 배정 2단계의 부서 드롭다운은 `features/department`의 `useDepartmentsQuery`(`DEPTS`, `GET /api/departments`)를 **그대로 재사용**한다(신규 조회 훅 생성 금지). 활성 부서만 선택 대상이므로 `isActive=true` 필터로 조회한다.
- **로그인 + 세션 복원** — auth·shell PRD 관할(`LOGIN`/`REISSUE_TOKEN`/`RETRIEVE_ME_INFO`). 본 도메인은 진입 전제로만 사용하며 재구현하지 않는다.
- **role 게이팅** — 라우트 가드·사이드바 노출은 기존 `ProtectedRoute`/`hasRequiredRole`(minRole `HR`)를 소비한다. 신규 게이팅 로직 없음.

### 3. MVP 이후 기능 / 범위 외 (이번 PRD 명시적 제외)

- **가입 승인 거부/반려** — 백엔드에 대응 엔드포인트 없음(발명 금지).
- **기존(현재) 소속 수정** — `HR_UPDATE_EMP_BELONGINGS`의 `deptId=null`(현재 소속의 직급/기간만 수정) 케이스. 향후 사원 상세/관리 화면 소관.
- **퇴직/정직/활성화·사원 개인정보 수정·사원 파일 관리·관리용 사원 목록** — EmpManagementApi의 다른 기능(별도 PRD).
- **테마/다크모드·다국어(i18n)·브라우저 푸시 알림** — 전 도메인 공통 제외.

## 📄 페이지별 상세 기능

### P1. 신규 사원 승인 페이지 (가입대기자 목록)

> **구현 기능:** `F001` (+ P2 다이얼로그 host) | **메뉴 위치:** 인사관리 > 신규 사원 승인 | **라우트(참고):** `/employees/new`(대안 `/hr/registrations` — 최종 결정은 development-planner)

| 항목 | 내용 |
|---|---|
| **역할** | 가입대기자(PENDING)를 페이징 목록으로 조망하고, 이름으로 검색하며, 개별 승인 마법사로 진입하는 랜딩 화면 |
| **진입 경로** | 사이드바 "인사관리 > 신규 사원 승인"(minRole HR) · 승인 완료 후 목록 갱신 |
| **접근 권한** | 최소 요구 role: `HR`(ADMIN 자동 포함) / 서버 최종 판단: role만 판정(같은 부서 등 관계 조건 없음, `ROLE_003` 해당 없음). 비HR·비ADMIN URL 직접 진입 시 라우트 가드가 차단 |
| **사용자 행동** | 이름 검색어 입력(디바운스), 페이지 이동, 특정 행의 `[승인]` 클릭 |
| **주요 기능** | • 가입대기자 페이징 테이블 렌더(F001 · `@tanstack/react-table`, 컬럼: 사원번호·이름·로그인ID·이메일·내선번호) • **이름 검색** 입력(keyword, 미입력=전체 PENDING) • 페이지네이션(Spring `Page` 메타: `totalPages`/`number`/`first`/`last`) • 행별 **[승인]** 버튼(→ P2 다이얼로그, 대상 empId 전달) • 빈 목록 시 "가입 대기 중인 사원이 없습니다" 안내 |
| **다음 이동** | `[승인]` → 승인 마법사 다이얼로그(P2). 조회 실패 → 에러 토스트(sonner). 승인 마법사 완료 → 목록 쿼리 invalidate(승인된 사원은 ACTIVE가 되어 목록에서 사라짐) |

### P2. 승인 마법사 다이얼로그 (가입 승인 → 조직 소속 배정)

> **구현 기능:** `F002`(1단계), `F003`(2단계) | **메뉴 위치:** (비노출) P1 행별 [승인] | **형태:** 목록 위 모달, **2단계 마법사**(단계 표시기 포함)

| 항목 | 내용 |
|---|---|
| **역할** | 한 대기자를 대상으로 ①가입 승인 → ②조직 소속 최초 배정을 하나의 연속 플로우로 처리하는 화면 |
| **진입 경로** | 신규 사원 승인 페이지(P1)의 행별 `[승인]` 버튼(대상 empId·이름 컨텍스트 전달) |
| **접근 권한** | 최소 요구 role: `HR`(ADMIN 자동 포함) / 서버 최종 판단: role만(관계 조건 없음). 각 단계는 서버가 상태·입력을 최종 검증(도메인 에러 → 토스트) |
| **사용자 행동** | **1단계**: 입사일자(hiredAt) 선택 → `[승인]`. **2단계**(승인 성공 후 자동 도달): 부서 선택·직급 선택·주요소속 확인·발령시작일 선택 → `[소속 배정 완료]` |
| **주요 기능** | **① 가입 승인 단계(F002)**: • 대상 사원 요약(이름·로그인ID) • 입사일자 date 입력(zod: yyyy-MM-dd, 필수) • **[승인]** 버튼 → `PATCH .../registration-approval?hiredAt=`(바디 없음) • 성공(204) 시 2단계로 전진 · 실패 시 1단계 유지<br>**② 조직 소속 배정 단계(F003)**: • **부서** 선택(`useDepartmentsQuery`, isActive=true 재사용, 필수) • **직급** 선택(PositionCode enum 드롭다운, 필수) • **주요소속여부** — 최초 배정이라 항상 `true`(읽기전용 표시 또는 기본 체크, 요청엔 항상 포함) • **발령시작일**(startAt, yyyy-MM-dd, 필수, 기본값=1단계 입사일자) • `endAt` 미수집(null) • **[소속 배정 완료]** 버튼 → `PATCH .../belongings`(4필드 바디) |
| **다음 이동** | 1단계 승인 성공 → 2단계 자동 전진. 2단계 배정 성공(204) → 다이얼로그 닫고 P1 목록 invalidate + 성공 토스트. 1단계 실패(이미 ACTIVE 등) → 에러 토스트 후 다이얼로그 닫고 목록 갱신. 2단계 실패(부서 미존재·필수누락 등) → 에러 토스트, **2단계 유지(재시도는 소속배정만 재호출, 승인 재호출 금지)** |

| P2 1단계(승인) | employee(신규) | `HR_APPROVE_EMP_REGISTRATION` | Path `empId:number` · Query `hiredAt:string(yyyy-MM-dd, 필수)` · **요청 바디 없음** → `204` Empty | PATCH `/api/employees/{empId}/registration-approval?hiredAt=`. PENDING→ACTIVE, PENDING 상태에서만 가능 |
| P2 2단계(소속) | employee(신규) | `HR_UPDATE_EMP_BELONGINGS` | Path `empId:number` · 요청 `{ deptId:number, position:PositionCode, isPrimary:boolean, startAt:string(yyyy-MM-dd), endAt:string\|null }` → `204` Empty | PATCH `/api/employees/{empId}/belongings`. **신규 소속 등록**: `deptId·position·isPrimary·startAt` 4개 필수(하나라도 null이면 "수정" 케이스로 오인 → IllegalArgumentException). `endAt` 미수집(null). 신규 타입 `EmpBelongingsCreatePayload` + `PositionCode`/`positionLabels`(신규) |
| P2 2단계 부서선택 | department(재사용) | `DEPTS`(기존) | `useDepartmentsQuery({ isActive:true })` → 부서 옵션 `{ deptId, deptName }` | GET `/api/departments`. 신규 조회 훅 생성 금지, 기존 `features/department/api/useDepartmentsQuery.ts` 소비 |

**계약 실측 메모(스니펫 직접 대조):**

- **승인은 바디 없는 PATCH**: `HR_APPROVE_EMP_REGISTRATION` http-request는 `Content-Type: application/x-www-form-urlencoded`에 바디가 비어 있다. `hiredAt`은 **쿼리 파라미터만** 사용(axios `patch(url, null, { params: { hiredAt } })` 형태).
- **PositionCode enum(백엔드 실측)**: `NONE`(미지정)·`INTERN`(인턴)·`STAFF`(사원)·`SENIOR_STAFF`(주임)·`ASSISTANT_MANAGER`(대리)·`MANAGER`(과장)·`SENIOR_MANAGER`(차장)·`DIRECTOR`(부장)·`EXECUTIVE`(임원). 프론트에 `positionName`(표시문자열)만 있고 `position`(코드)용 타입/라벨맵은 없으므로 **`PositionCode` 타입 + `positionLabels` 신규 작성**. 직급은 필수 non-null이므로 드롭다운은 미선택 상태를 허용하지 않는다.
- **신규 소속 등록 vs 수정 판별**: `deptId`가 non-null이면 서버가 "신규 소속 등록"으로 처리하며 이때 `position·isPrimary·startAt`도 반드시 non-null이어야 한다(request-fields "신규 소속 등록 시 필수"). 이번 PRD는 최초 배정만 다루므로 폼은 **항상 4필드를 채워 전송**한다(`deptId=null` 수정 케이스는 만들지 않음).
- **주요소속(isPrimary)**: 최초 배정이라 사실상 항상 `true`. 서버는 새 primary 등록 시 기존 primary를 자동 비활성화하므로(도메인) 프론트는 별도 처리 불요. 표시는 읽기전용/기본 체크로 두되 요청 바디엔 `true`를 포함한다.
- **endAt**: request-fields상 optional(현재 진행 소속은 null). 최초 배정은 종료일이 없으므로 **미수집(null)** → `END_TIME_BEFORE_START_TIME_EXCEPTION`은 이 플로우에서 발생 여지 없음.
- **응답 코드**: 목록 `200`(Page), 승인 `204` Empty, 소속 배정 `204` Empty.

**에러/엣지케이스(전역 `handleApiError` 소비 · 코드/메시지 계약은 CLAUDE.md §7 관할):**

- **이미 승인된 대상 재승인**: 목록은 PENDING만 노출하므로 정상 경로엔 없으나, 동시성(다른 HR가 먼저 승인) 시 서버 `ACTIVE_EMPLOYEE_NOT_FOUND_EXCEPTION` → 에러 토스트 후 다이얼로그 닫고 목록 갱신.
- **부서 미존재(deptId)**: 드롭다운은 유효 부서만 제공하나, 그 사이 비활성화 등으로 `DEPT_NOT_FOUND_EXCEPTION` 발생 가능 → 에러 토스트, 2단계 유지.
- **필수값 누락(4필드 중 하나라도)**: zod 사전검증으로 1차 차단. 우회 시 서버 `REQUIRED_VALUE_MISSING_EXCEPTION`/IllegalArgumentException → 에러 토스트.
- **승인 성공 후 소속배정 실패**: 대상은 이미 ACTIVE이므로 **승인을 재호출하면 안 된다**(재호출 시 도메인 에러). 마법사 2단계에 머문 채 소속배정만 재시도한다.
- **승인 후 소속배정 전 다이얼로그 이탈**: 대상은 ACTIVE지만 주요소속 미배정 상태로 남는다(PENDING 목록에서 사라져 이 화면에선 재진입 불가). 2단계에서 닫기 시도 시 경고("승인은 완료되었으나 소속이 배정되지 않았습니다") 노출 권장 — 이런 사원의 사후 소속 배정은 향후 사원 관리 화면 소관(Open Q#2).

## ❓ Open Questions (착수 전 사용자·검증 확인 필요)

1. **라우트 경로.** `/employees/new`(API 경로·향후 `/employees/:empId`와 정합) vs `/hr/registrations`(인사관리 그룹 의미 강조) 중 택1. **권고:** `/employees/new`(리소스 경로 컨벤션 `/departments`·`/department-members`와 정합). 최종 결정은 development-planner/react-router-developer 단계.
2. **승인 후 소속 미배정 사원의 사후 배정 경로.** 백엔드는 승인(ACTIVE 전환)과 소속 배정을 별도 호출로 분리하므로, 2단계 이탈 시 "ACTIVE·주요소속 없음" 사원이 생길 수 있다. 이번 PRD는 이탈 시 경고로 완화하고, **사후 재배정은 향후 사원 관리 화면(`EMPS_FOR_MANAGEMENT` + `HR_UPDATE_EMP_BELONGINGS`)에서 처리**하는 것으로 격리. 이탈 방지를 더 강하게(닫기 차단) 할지 확인 필요.
3. **직급 기본값·NONE 노출.** PositionCode `NONE`(미지정)을 드롭다운에 노출할지, 기본 선택값을 무엇으로 둘지(예: 미선택 강제 vs `STAFF` 기본). **권고:** 전체 enum 노출 + 미선택 강제(필수 필드라 명시적 선택 유도).
4. **슬라이스 배치.** 3개 엔드포인트가 전부 `/api/employees/*`이고 HR 관리 인프라가 이미 `features/employee`(EMPS_FOR_MANAGEMENT·HR mutation)에 있으므로 **`features/employee` 하위(예: `features/employee/registration` 그룹)** 배치를 권고. 새 `features/hr` 신설은 과함. 최종 폴더 구조는 development-planner 확정.
